# Проверка в платформе: девять уровней без участия человека

Структурные проверки (`check_project`, `check_bsl`) и EDT ловят формат. Всё,
что 1С показывает «только в бою» — пути к данным, реструктуризация,
компиляция запросов СКД, серверный код на настоящих данных, раскладка форм, —
проверяется в самой платформе. Инструмент — `tools/platform.py` с настройками
в `platform.json` проекта (пример — `bootstrap/platform.json.example`).
Уровни отработаны на проекте EAM (8.5.1) и МВМ (8.3.27), сентябрь 2026.

| Уровень | Команда | Что ловит | Время |
|---|---|---|---|
| 1. Загрузка | `platform.py <json> load [rev]` | «Неверный путь к данным», несовместимые свойства, ошибки реструктуризации — то, что EDT validate не видит | 5–20 мин |
| 1a. Быстрая | `platform.py <json> quick` | то же после правки ТОЛЬКО модулей `.bsl`: без экспорта EDT | 1–2 мин |
| 2. Обновление ИБ | `platform.py <json> update` | обработчики обновления БСП и свои, «Начальное заполнение» | 1–10 мин |
| 3. Внешнее соединение | `platform.py <json> com counts / reports / query / call` | серверный код и запросы на настоящих данных; все варианты всех отчётов компонуются | секунды |
| 4. Снимки форм | `platform.py <json> screens [шаг] [маски]` | пустые формы, разъехавшаяся раскладка, модальные диалоги при открытии | минуты |
| 5. Все формы | `platform.py <json> forms [префикс…]` | падения `ПриСозданииНаСервере`/`ПриОткрытии` любой своей формы: «Поле объекта не обнаружено», «Несоответствие типов», «не определена» | минуты |
| 6. Заполненность | `platform.py <json> com fill [порог]` | реквизиты, которые посев/обработчики оставляют пустыми (по всей таблице) | секунды |
| 7. Прогон сценария | демо-посев / свой сценарий через `com call` или клиент по `/C` | ключи регистров, проведение цепочек документов, «второй документ на тот же ключ» (case 064) | минуты |
| 8. Страницы поля HTML | снимок страницы с данными + headless-браузер + клиент | JS-ошибки, раскладка вкладок, обмен страница ↔ 1С (щелчки, пакеты) | минуты |
| 9. Настоящие нажатия | `platform.py <json> ui <сценарий>` или `vanessa.py <json> <фичи>` (Vanessa Automation, §9а) | видимость/доступность команд, `ПриИзменении` от ввода, выбор из подсказки, проверки заполнения при проведении, цепочки «на основании» | минуты |

Уровень 3 работает и на РАБОЧЕЙ базе (только чтение): на МВМ `com reports`
скомпоновал девять отчётов за секунду — ошибка «Неоднозначное поле»
(case 062) была бы поймана до пользователя.

## 1. Загрузка в пустую базу

`1cedtcli export` → `1cv8 CREATEINFOBASE` → `DESIGNER /LoadConfigFromFiles`
→ `/UpdateDBCfg`, логи через `/Out`. Проверять можно и git-ревизию проекта
(`load <rev>`: `git archive` во временную папку) — так сравнивают «до» и
«после».

Только так ловится запрос динамического списка, который платформа не компилирует («Неверный путь к данным»
по всем полям списка): EDT validate молчит, инкрементальная загрузка неизменённую форму не перепроверяет (case 063).

- EDT CLI пишет в консоль в cp866 и требует ОТДЕЛЬНОЕ рабочее пространство
  (`-data`), иначе мешает открытому EDT.
- `DESIGNER` без `/DisableStartupDialogs /DisableStartupMessages` замирает
  на любом диалоге (см. `deployment.md`).
- Модули в выгрузке Конфигуратора — С BOM, в проекте EDT — без: при переносе
  `.bsl` в `quick` читать `utf-8-sig` и писать `utf-8-sig`.
- Соответствие путей `src/…/Module.bsl` → `…/Ext/Form/Module.bsl` — в
  `xml_path()`; менялось не только `.bsl` → нужен полный `load`.

## 2. Первый запуск и обновление ИБ

Быстрее всего — внешним соединением:
`ОбновлениеИнформационнойБазы.ВыполнитьОбновлениеИнформационнойБазы()` даёт
полный текст ошибки с обработчиком. Запасной путь — клиент с параметром БСП
`/C ЗапуститьОбновлениеИнформационнойБазы;ЗавершитьРаботуСистемы`; ошибки
читаются из журнала регистрации (`1Cv8Log\*.lgp`, текстовый формат, уровень
`E`), и как только там появляется «При вызове обработчика обновления», клиента
ЭТОЙ базы надо убить — иначе он висит на окне «Не удалось выполнить
обновление». Клиентов останавливать по командной строке процесса (путь к
базе), а не всех `1cv8*` подряд.

## 3. Внешнее соединение (COM)

- Коннектор по версии платформы базы: `V83.COMConnector` для 8.3.x,
  `V85.COMConnector` для 8.5.x; разрядность dll = разрядности Python.
- **`regsvr32 comcntr.dll` без прав администратора падает** (0x80070005), а
  без регистрации `Dispatch` создаётся, но `Connect` «не найден»:
  «Библиотека не зарегистрирована» — не зарегистрирована библиотека ТИПОВ.
  Регистрация на пользователя: `tools/register_com.py` с путём к comcntr.dll
  (HKCU CLSID + ProgID + `RegisterTypeLibForUser`). `regsvr32 /n /i:user`
  не годится: у comcntr нет DllInstall.
- Строка соединения: `File="…";Usr="…";Pwd="…";` (или `Srvr`/`Ref`). Без
  пользователя на базе с пользователями — «Неверно указан пользователь или
  пароль». Пароли в `platform.json` не хранить; пустой пароль допустим.
- Внешнему соединению недоступны глобальные функции клиента и часть
  контекста (`ДобавитьМесяц` и т.п. считать на стороне Python, даты
  передавать готовыми); форм там нет вовсе — для форм уровень 4.
- Отчёты: `ПолучитьМакет(ОсновнаяСхема)` → для каждого варианта
  `КомпоновщикНастроек.Инициализировать` + `ЗагрузитьНастройки`, пустым
  параметрам-датам и стандартным периодам подставить последние 12 месяцев,
  `СкомпоноватьРезультат(ТабличныйДокумент, ДанныеРасшифровки)`. Ошибка
  компоновки — с полным текстом (`excepinfo[2]` у `com_error`).
- Свои процедуры: `com call Модуль.Функция арг…` — серверный общий модуль с
  экспортом; демо-посев так и запускают (структуру параметров собирает
  `cn.NewObject("Структура")`).

## 4. Снимки форм тонкого клиента

В XML-КОПИЮ (не в проект!) добавляются три вставки между метками
`// ТЕСТ-СКРИНШОТЫ begin/end`: серверный модуль хранит список форм и индекс в
`ХранилищеОбщихНастроек` (у глобального клиентского модуля нет переменных
между вызовами), глобальный клиентский модуль по обработчику ожидания
открывает следующую форму (`ОткрытьФорму(Имя)` в `Попытка`), а
`ОбщегоНазначенияКлиентПереопределяемый.ПослеНачалаРаботыСистемы` запускает
обход по `/C СкриншотыФорм`. Скрипт следит за индексом через COM и снимает
ТОЛЬКО окно процесса этой базы (`PrintWindow` по дескриптору, окно
разворачивается `ShowWindow 3`) — чужие окна на экране не мешают. Клиент
переключает форму вдвое реже, чем скрипт снимает: первое открытие формы в
тонком клиенте медленное. Если индекс не растёт минуту — снимок `stall_NN.png`
показывает, что блокирует: вопрос, предупреждение, ошибка.

Нужны три модуля конфигурации (в `platform.json`, раздел `screens`): любой
серверный `…ВызовСервера`, любой глобальный клиентский (`<global>true`,
клиентское приложение) и переопределяемый БСП. У своей конфигурации без БСП
— завести их в XML-копии или взять другие точки входа.

## 5. Все формы: ПолучитьФорму в клиенте

`forms` добавляет в XML-копию обход своих форм по `/C ПроверкаФорм`:
`ПолучитьФорму(Имя, , , Новый УникальныйИдентификатор)` в `Попытка` (форма создаётся,
но не показывается), итог — в `ХранилищеОбщихНастроек`, скрипт читает его через COM,
клиент завершается сам. На EAM из 307 форм так нашлись «Поле объекта не обнаружено
(ПапкаДляДобавления)», «Несоответствие типов» в формах документов и падения
`ПриСозданииНаСервере` после переименований.

- Формы, которым нужен контекст (форма перетаскивания файлов без параметров, форма
  элемента присоединённого файла без ключа, форма подбора из записанного документа),
  падают ОЖИДАЕМО. Список ожидаемых держать в проекте и сравнивать прогоны, а не чинить
  «вслепую».
- Открытие формы на пустой базе и на базе с данными — разные проверки: на данных
  всплывают ошибки обработчиков заполнения (уровень 7 перед уровнем 5).

## 6. Заполненность данных

`com fill [порог]` считает долю пустых значений каждого реквизита своих справочников и
документов (шапка и ТЧ) запросом по ВСЕЙ таблице. Выборка «первые 300 строк» обманывает:
назначение, основание и т.п. часто заполнены только у части строк. По умолчанию
печатается то, что пусто всегда (порог 100). Пусто по смыслу — изображения,
доп. реквизиты, дата увольнения, служебные реестры; остальное — пробелы посева или
обработчиков. На EAM так нашли ~100 всегда пустых реквизитов и одного автора у всех
документов демо-базы.

## 7. Прогон сценария как интеграционный тест

Генератор демо-данных (или свой сценарий) проводит цепочки документов так же, как
пользователь: заказ → акт → списание, основной → корректировочный документ. Запуск —
`com call Модуль.Функция` или клиентом по `/C` (длинные сценарии), журнал — в
`ЖурналРегистрации` / хранилище настроек. Такой прогон нашёл то, что пропустили
ручные проверки: регистр, в который два документа пишут один ключ (case 064), запрос
к справочнику без кода (case 065). После прогона — уровни 3 (отчёты на данных) и 6.

Ловушка прогона (МВМ): **начальная страница пользователя может быть пустой** — личная
настройка сильнее `HomePageWorkArea.hpwa`, и клиент, поднятый для сценария, не открыл АРМ
вовсе (раздача по таймеру формы не шла, ошибок нигде). Сценарий не полагается на начальную
страницу: форму открывает параметр запуска (`/C "АРМДиспетчера;Автораспределение"` —
вставка в `ПослеНачалаРаботыСистемы`, флаг читает `ПриОткрытии` формы). Вторая: автораздача
на копии РАБОЧЕЙ базы выбирает из всего парка, и лист уходит машине без водителя — заявке
сценария задавать тип ТС машины с телефоном. Проведённые документы копии типовая может не
дать перепровести — чистку данных вести до транзакции посева и пропускать с причиной.

## 8. Страницы поля HTML (дашборды, справка)

Страница в поле HTML — отдельная программа на JS: её ошибки не видны ни EDT, ни
платформе.

- **Снимок с данными.** Во вставке XML-копии форма пишет собранную страницу (шаблон +
  данные) в файл; её открывает headless-браузер — быстрые итерации без 1С
  (подставлять новый шаблон к снятым данным).
- **Headless Edge:** старый режим `--headless` (в `--headless=new` снимок не пишется),
  своя `--user-data-dir`, `--virtual-time-budget`; `msedge.exe` возвращается РАНЬШЕ,
  чем появляется PNG — ждать файл. Вставка тестового скрипта — перед ПОСЛЕДНИМ
  `</body>`: строка `</body>` встречается внутри кода библиотек (ECharts).
- **Проверка в движке 1С обязательна:** движок поля HTML — не браузер (ES5, свои
  ограничения). Вставка в XML-копии открывает нужную вкладку, скрипт снимает окно.
  Если данные приходят фоном (case 066), щёлкать вкладку ПОСЛЕ снятия заставки загрузки.
- **Обмен страница → 1С** проверяется вызовом обработчика `ПриНажатии` формы с теми же
  ссылками, что формирует страница (`Новый Структура("href", "…#действие-…")`), по
  списку всех действий; итог — «ок / текст ошибки» на каждое (case 069).

Образцы проверок уровней 7–8 (ФРЕГАТ EAM, пути зашиты — брать как шаблон):
`reference/testing-eam/platform_dash.py` (снимок страницы с данными и вкладки в клиенте),
`dash_shots.py` (вкладки в headless Edge), `platform_click.py` (все действия страницы через
обработчик `ПриНажатии`), `audit_fill.py` (первая версия аудита заполненности).

## 9. Настоящие нажатия: управляющий клиент ведёт тестируемый

Уровни 5 и 7 вызывают обработчики из тестовой вставки — видимость и доступность
команд, события `ПриИзменении` от ввода, выбор из подсказки, проверки заполнения
при проведении ими не проверяются. Уровень 9 — штатное автоматизированное
тестирование платформы: клиент `/TESTCLIENT -TPort <порт>` открыт как у
пользователя, второй клиент той же базы `/TESTMANAGER` через
`ТестируемоеПриложение` находит элементы и нажимает, вводит, выбирает.

```
python tools/platform.py <platform.json> ui <сценарий.txt> [порт=48123]
```

Сценарий — строки «шаг | арг1 | арг2 | арг3», `#` — комментарий
(образец: `reference/testing-ui/eam_defect_order.txt`, 27 шагов, ФРЕГАТ EAM):

| Шаг | Аргументы | Что делает |
|---|---|---|
| `команда` | навигационная ссылка | `ВыполнитьКоманду("e1cib/list/Документ.X")` в основном окне |
| `форма` | часть заголовка | ждать активную форму (до 30 с) |
| `кнопка` | имя элемента или заголовок | `Нажать()` |
| `поле` | имя, текст | ввод и уход из поля — отрабатывает `ПриИзменении` |
| `ссылка` | имя, набрать, [выбрать] | ввод части наименования + выбор строки подсказки |
| `выбор` | имя, значение | выбор из списка выбора поля |
| `значение` | имя, [ожидаемое] | отображаемый текст; не содержит ожидаемое — ошибка |
| `добавить` / `ячейка` / `завершить` | таблица / колонка, текст / таблица | новая строка ТЧ, ввод в ячейку, конец редактирования |
| `строка` / `открыть` | таблица, первая\|последняя\|следующая | переход по строкам / открыть текущую |
| `сообщения` | [ожидаемое] | сообщения пользователю основного окна |
| `снимок` | имя | PNG окна тестируемого клиента (`screens/ui_<имя>.png`) |
| `дамп` | — | окна, активная форма, сообщения, дерево элементов |
| `ждать` | секунд | пауза |

Шаги менеджера-обработки (`reference/testing-ui/ТестUIМенеджер.Module.bsl`, проекты ZHDRM и UP, 8.5.1) —
дополнительно к таблице выше (case 085):

| Шаг | Аргументы | Что делает |
|---|---|---|
| `выбор` | имя поля | кнопка выбора («…») — `Выбрать()`; ссылочное поле шапки или ссылочная ячейка после `изменить` |
| `выделить` | таблица | `ВыделитьВсеСтроки()` — панель множественного выделения 8.5 |
| `закрыть-форму` | начало заголовка | закрыть активное окно, только если заголовок его формы начинается так |
| `закрыть` | [`без сохранения`] | закрыть активное окно; «без сохранения» — ответить «Нет», если 1С спросит |
| `?<шаг>` | как у шага | необязательный: ошибка пишется «ПРОПУЩЕН», сценарий идёт дальше |
| `раздел` | заголовок раздела | кнопка раздела командного интерфейса (8.5 не открывает `e1cib/navigationpoint`) |

**Скорость (case 092, UP 17.10.2026: обзор 176 шагов ~1700 с → 110 с).** Снимок — копией экрана (`PIL.ImageGrab` по прямоугольнику главного окна PID): `PrintWindow` тормозит следующую загрузку динамического списка на десятки секунд. Весь сценарий — одним клиентом (ожидание 40 с × шагов), менеджер собирать, только если исходники новее `.epf`, журнал опрашивать каждые 0,2 с; в журнале у каждого шага — `[N мс]`. Ошибки текста запроса ловить до платформы: `designer_lib.check_query`, линт модулей и `QueryText` форм.

Итог — «ОК/ОШИБКА строка => результат», код возврата 1 при ошибке. На первой
ошибке сценарий останавливается и печатает состояние (дерево элементов формы
с именами, типами, заголовками) — по нему пишется следующий шаг. Новую форму
начинать с разведки: `команда → форма → дамп`.

Механика (всё — в XML-копии, проект не меняется):
- серверный модуль: сценарий, итог и сигнал «снимок» через ХранилищеОбщихНастроек
  (Python пишет сценарий по COM, ждёт итог, по сигналу снимает окно и сбрасывает флаг);
- глобальный клиентский модуль: интерпретатор `ТестUIВыполнить`;
- модуль после начала работы: `/C СценарийUI` → интерпретатор → завершение.

Фактические имена методов — `reference/testing-ui/test_api_8.5.1.md` (сняты с
`bin/test.dll`): справка и память модели ошибаются (case 071).

Прогон на ФРЕГАТ EAM: дефект → смета → заказ на ремонт за ~15 с сценария
(загрузка вставок 0,3 мин). Первый же прогон нашёл, что форма дефекта не
заполняет организацию и подразделения по объекту эксплуатации — заказ в конце
цепочки не проводился; исправлено в генераторе, прогон зелёный.

### 9а. Vanessa Automation — тот же уровень готовой библиотекой шагов

Vanessa Automation (github.com/Pr-Mex/vanessa-automation, внешняя обработка, релиз «single» — один
`vanessa-automation-single.epf`, 23 МБ) работает на том же механизме TestManager → TestClient, но
сценарии пишутся на русском Gherkin из ~800 готовых шагов, есть отчёты JUnit/Allure и снимки при ошибке.
Для сценариев, которые будут жить с проектом (регресс, демонстрации, приёмка), — это основной инструмент;
`platform.py ui` — для разведки формы (дамп дерева элементов) и там, где Vanessa нет.

```
python tools/vanessa.py <platform.json> <каталог фич или .feature> [тег]
```

`platform.json`: `"va_epf": "<путь к vanessa-automation-single.epf>"` (скачивать вне проекта,
с согласия пользователя), `"va_port"` (по умолчанию 48000), `"va_ib"` — другая файловая база вместо
`work/ib` (например, копия рабочей базы для сдачи: сценарии на настоящих данных). Инструмент собирает `VAParams.json`
(плоский формат, ключи — как в папке tools/JSON репозитория VA), запускает
`1cv8 ENTERPRISE /F<база> /TESTMANAGER /Execute <epf> /C"StartFeaturePlayer;VAParams=<json>"`,
закрывает клиенты тестовой базы и печатает итог JUnit; при падении — лог шагов со временем.
Результаты — `<work>/va_out` (junit, log.txt, status.log, screens). Код возврата 0 — все сценарии прошли.

Образец: `reference/testing-ui/eam_defect_order.feature` (35 шагов, дефект → смета → заказ, 34 с).
Опорные шаги (точные формулировки — из библиотеки VA, не по памяти):

```gherkin
Дано Я открыл новый сеанс TestClient или подключил уже существующий
Когда я перехожу по навигационной ссылке "e1cib/list/Документ.eamВыявленныйДефект"
Тогда открылось окно "Выявленный дефект (создание)"
И я нажимаю на кнопку с именем 'ФормаСоздать'
И из выпадающего списка с именем 'ОбъектЭксплуатации' я выбираю по строке "Насос шламовый"
Тогда элемент формы с именем 'Организация' стал равен шаблону "*меридиан*"
И поле с именем 'СтоимостьРабот' заполнено            # число 0 — «не заполнено»
И в таблице "ПлановыеСрокиРемонта" я нажимаю на кнопку с именем 'ПлановыеСрокиРемонтаДобавить'
И в таблице "ПлановыеСрокиРемонта" в поле с именем 'ПлановыеСрокиРемонтаПлановаяДата' я ввожу текст "15.10.2026"
И в таблице "ПлановыеСрокиРемонта" я завершаю редактирование строки
Тогда в окне сообщений пользователю нет сообщений
```

**Много фич — один запуск.** Старт менеджера и тест-клиента стоит 1–2,5 мин на каждый запуск
`vanessa.py`, поэтому регресс собирать в одну папку и пускать разом. Связь между фичами — код в
самом сценарии (проверено на VA 1.2.043):

```gherkin
И я выполняю код встроенного языка на сервере        # сервер менеджера = тестовая база
"""bsl
	Объект.ЗначениеНаСервере = Формат(Число(Лист.Номер), "ЧГ=");   # ВызватьИсключение — падение шага
"""
И я запоминаю значение выражения 'Объект.ЗначениеНаСервере' в переменную "Лист"
И в таблице "Рейсы" я перехожу к строке:            # $Лист$ подставляется и в ячейки таблицы
	| 'Номер'  |
	| '$Лист$' |
И я делаю 40 раз                                     # цикл; «Пока» переменную не перечитывает
	Если 'Контекст.Есть = "1"' Тогда                 # выражение видит Контекст
		И я нажимаю на кнопку с именем 'Дальше'
Если элемент формы с именем "Поле" присутствует на форме Тогда   # шага «видим» нет
```

**Видео прогона** (демонстрация, приёмка, разбор падения): `vanessa.py … --video [файл.mp4]`.
Запись всего рабочего стола ffmpeg (gdigrab, 15 кадр/с, H.264): начинается, когда запущен тестируемый
клиент (процесс с `/TESTCLIENT`), и заканчивается с прогоном; в копию сценариев после шага подключения
добавляется «И я активизирую главное окно сеанса TESTCLIENT» — без него клиент остаётся под окном менеджера
Vanessa. `platform.json`: `"ffmpeg"` (или ffmpeg в PATH), `"va_video_dir"` — каталог видео (`va_out`
очищается каждым прогоном). Сценарий EAM: ~1 мин, ~2 МБ. В кадр попадает весь экран, включая
всплывающие уведомления других программ — перед публикацией проверять.

Ловушки Vanessa (МВМ, 12 сценариев заказчик/диспетчер/водитель): окно ввода строки
(`ПоказатьВводСтроки`) и всплывающее меню (`ПоказатьВыборИзМеню`) шагами не берутся — такие
сцены показывать руками, логику проверять через COM; строка таблицы выбирается только табличным
шагом «я перехожу к строке:» с колонкой и значением (без таблицы — «Недостаточно фактических
параметров»); одинаковые заголовки закладок («Основное» у формы и у внутренних страниц) — брать
закладку по имени; группа и поле с одним именем — шаг по имени попадает в группу; кнопка на
скрытой странице — «Не получилось нажать»; первое подключение TestClient не всегда успевает —
сценарий-разогрев первым; `platform.py ui` правит модули XML-копии — в базу оттуда грузить
только модули, взятые из проекта. Видео: пока идёт запись, не запускать других команд —
окно клиента уходит под другие окна.

Имена элементов для шагов — из дампа `platform.py ui` (шаг `дамп`) или из `Form.form`.
Список всех шагов снимается с исходников VA: `features/Libraries/*/step_definitions/**/Module.bsl`,
регистрации `ДобавитьШагВМассивТестов(ВсеТесты, "<процедура>", "<имя>", "<текст шага>", …)`
(в том числе с префиксом `Ванесса.`), плюс `VanessaAutomation/Templates/ЧастоИспользуемыеШаги`.

## Ловушки клиента в тестах

- **Масштаб экрана не 100 %:** без `SetProcessDPIAware` снимок `PrintWindow` обрезан
  (логический размер окна против физического). В `SHOT_PS` исправлено.
- **Повторный запуск клиента** сразу после `Stop-Process` часто не открывает окно —
  пауза ~15 с между прогонами.
- **Вставки BSL в Python-строках:** кавычки BSL удваиваются (`""`), обратная косая
  черта в BSL не экранирует; тройные кавычки BSL внутри `"""…"""` Python закрывают
  строку — собирать вставку конкатенацией или в отдельном файле.
- **Фантом отрисовки вкладок:** вкладка, впервые показанная шагом `Активизировать()` после возврата из другого окна
  (отдельная форма), в тестовом клиенте может остаться пустой при верных данных — проверять переключением из кода формы
  (case 075), не переписывать работающий код.
- **Пустая форма в кадре — модальное окно** (`ИмяАктивнойФормы: ErrorWindow` в ошибке шага Vanessa): окно вопроса
  или ошибки — отдельное окно процесса 1cv8c (~670×266, «1С:Предприятие»), в видео и в снимок главного окна не
  попадает. Снимать КАЖДОЕ окно процесса шагом сценария (case 089, `after/все_окна.py`; ср. case 079); снимок
  всего экрана не годится — клиент копии бывает позади, в кадр попадает рабочий стол пользователя.
- **Снимок окна тестового клиента — по своему порту** (`TPort <порт>`), не по `TESTCLIENT`: на общем сервере
  параллельно может идти UI-прогон другого проекта, и снимок захватит его окно (case 077).
- **Headless Edge — из PowerShell.** Из Bash-инструмента (Git Bash) `msedge --headless` на Windows Server молча
  пуст (код 0); проверки страниц поля HTML (`--dump-dom`, `--screenshot`) запускать из PowerShell (case 076).
- **Окна тестового клиента видит пользователь**, если работает за тем же компьютером:
  ошибка тестовой вставки выглядит как ошибка конфигурации. Предупреждать и закрывать
  клиентов ТОЛЬКО тестовой базы (по пути в командной строке процесса).
- **Пользователь тестовой базы:** после обновления типовой (УАТ) в базе есть
  «Администратор» — `/N` обязателен; в своей конфигурации без пользователей (EAM) `/N`
  несуществующего даёт «Пользователь ИБ не идентифицирован» — `"test_usr": ""`.
- **Окно авторизации при каждом запуске клиента** (пользователь жмёт «Войти»): пустой
  пароль платформа ждёт как `/P""`, а список аргументов `subprocess` экранирует кавычки —
  остаётся голое `/P`. Командную строку клиента собирать СТРОКОЙ (`client_cmd` в
  `platform.py`, `designer`); `/DisableStartupDialogs` окно НЕ подавляет — Конфигуратор
  тоже стоит с этим окном, пока не нажмут «Войти» (на МВМ «загрузка 13 минут» была ожиданием).
- **1cv8 из Git Bash** с путями `C:/…` падает за секунды без журнала — запускать из
  Python (`subprocess` со списком аргументов и обычными путями Windows).
- **Язык запросов через COM:** псевдоним `В` — ключевое слово (case 065); глобальные
  клиентские функции недоступны. Нет и `Формат`, `Строка`, `ТекущаяДата` — есть `String`, `XMLString`,
  `XMLValue`; серверные процедуры ФОРМЫ через COM не вызвать (только экспорт общих модулей и менеджеров);
  `НайтиПоНомеру` без даты при периодической нумерации пуст (case 090).
- **Тест-клиент 8.5.1 (case 085):** `Выбрать()` у строковой колонки с кнопкой выбора и своей формой по `StartChoice` —
  «Неподходящий тип элемента управления», после чего следующий шаг висит; стандартная «Записать» формы объекта висит —
  объект записывать через COM до прогона; формы с реальными данными — ~20 с на шаг: сценарий частями по 15–20 шагов
  (ожидание журнала 900 с), иначе «журнала нет» выглядит как зависание.
