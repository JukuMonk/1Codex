# Экспертиза задачи

Выполнять после краткого знакомства с запросом и проектом, до реализации.
Результат: существенные замечания с предлагаемым выходом, необходимые вопросы
владельцу решения и следующие действия по каждому пункту. Для обычной смены
подписи достаточно короткого заключения без замечаний. Не заполнять анкету ради формы.

## Как рассуждать

1. Разделить бизнес-правила, обязательные примеры, ограничения и предварительные
   идеи реализации. Условие, прямо заданное пользователем в постановке, уже принято,
   даже если отдельный список решений пуст.
2. Найти ответ в постановке, принятых решениях и нужных участках проекта. Имена
   метаданных и неизвестное поведение платформы выясняет разработчик. Различие
   текущего кода и нового требования само по себе не делает постановку противоречивой.
3. Для каждой критики указать источник, конкретный пример, последствие, своё
   предложение, компромисс и приёмочный сценарий. Отклонённую идею реализации
   также оформить замечанием, даже если правило уже принято. Осмысленная
   альтернатива необязательна; не предлагать отмену принятого правила ради старого кода.
4. Различать подтверждённое противоречие, недостающий бизнес-выбор, риск при
   названном условии и улучшение. Условное поведение сначала проверить. Не выдавать
   предположение за обнаруженный дефект.
5. Спрашивать владельца только о реально отсутствующем или несовместимом
   бизнес-правиле: один выбор, 2–3 варианта, последствия и рекомендация.
   Рекомендация не становится согласованным решением. Внешним адресатам вопросы
   автоматически не отправлять. Принятый ответ повторно не спрашивать.
6. Вопрос закрывает только зависимые пункты. Технический риск и необязательное
   улучшение сами по себе не останавливают задачу. Независимые действия продолжать.
7. Сохранять объём поручения. Более крупное изменение предложить отдельно.
   Приёмочные примеры COM, UI/Vanessa, статической или интеграционной проверки
   остаются планом до выполнения. Придуманные данные назвать будущей фикстурой.

Глубина: `quick` для локальной подписи или расположения без изменения данных;
`standard` для нового расчёта, объекта или пользовательского сценария;
`extended` для истории проведения, миграции, обмена, массовых или конкурентных
операций. При обнаружении влияния на историю можно повысить глубину и объяснить
причину. Наличие замечаний в согласованной задаче не считается ошибкой само по себе.
Режим не является доказательством скорости или автоматическим ограничителем чтения.

## Рабочий инструмент

`tools/workflow/expertise_cli.py` работает на стандартном Python 3.12+.
Путь к нему брать относительно установленного SKILL.md, без путей из чужого проекта.
В проекте подготовить профиль с версией платформы, форматом и областью работ.
Существующие карточки `task_plan.py` являются источником требований. Для небольшой
задачи без карточек подойдёт JSON `{"version":1,"points":{"P1":"Текст требования"}}`.
Решения задаются списком `{"id":"D1","points":["P1"],"text":"Принятый ответ"}`.
Если решений нет, список пуст; правила из самой постановки продолжают действовать.

Пример команд с путями текущего проекта:

~~~powershell
$expert = 'путь-к-плагину/tools/workflow/expertise_cli.py'
$work = '.platform/expertise/current-task'
python $expert init $work --source source --profile profile.txt --task-plan task-plan.json --journal $journal
python $expert start $work
python $expert search $work 'Артикул' --path-contains Catalogs
python $expert read $work 'source/Catalogs/Товары.xml' --first 90 --last 130
python $expert schema $work
python $expert submit $work --review review.json
python $expert check $work --point P1
python $expert show $work
~~~

Вместо `--task-plan` можно указать `--task requirements.json`.
Новый каталог экспертизы должен находиться вне дерева исходников; для карточек
он находится внутри их `project_root`. Исходники читаются из выбранного живого
каталога, поэтому изменение оригинала обнаруживается без копирования.
Для каждого нового задания создавать свой каталог; `start` в прежнем каталоге
начинает новую попытку и сохраняет историю заключений.

`start` возвращает постановку, профиль, решения и первые 160 строк индекса.
`read` отдаёт не более 160 строк; `search` не более 20 фрагментов.
Для ссылок в заключении использовать материал и номера строк, выданные этими
командами. Внешнее чтение не регистрируется автоматически: нужный фрагмент
следует получить через `read`. `schema` выводит полный контракт JSON.

Короткое заключение без замечаний имеет поля `mode`, `summary`, `findings: []`,
`questions: []`, `points` (id и next_action каждого пункта), `checked_sources`
(path, first, last) и `limitations`. Для замечания схема требует `proposal` и
приёмочные `given/when/then/level`; для вопроса связь с замечанием и зависимыми
пунктами. `submit` отклоняет незаполненное заключение и непрочитанные ссылки.

## Допуск, версии и монитор

Состояния: `ready`, `needs_decision`, `needs_review`, `unreviewed`.
При `--task-plan` подключение происходит автоматически. Начало этапа
`implementation` через `task_plan.begin_stage` проверяет актуальное заключение.
Для `__shared__` должны быть готовы все пункты; независимую реализацию отмечать
её собственным ID. Старые карточки без подключения продолжают работать.
Это проверка маршрута, а не запрет прямого редактирования файлов вне него.

`check --point` возвращает ненулевой код для закрытого пункта; `check` без ID
показывает все состояния. После ответа обновить `decisions.json` в каталоге
экспертизы и выполнить `start`, нужные чтения и `submit`. Для привязанной карточки
изменять саму карточку: её новая редакция читается автоматически.

Требования и решения инвалидируют затронутые пункты. Пока изменение любого
исходника требует пересмотра всех пунктов; после собственных правок перед началом
реализации следующего пункта также сверить актуальный контекст и записать новое
заключение. Повторный просмотр ограничить существенными зависимостями. Карта
зависимостей из лабораторного опыта в этот выпуск не переносится.

В «Мониторе 1Codex» появляется отдельная ветвь: источники, экспертиза, проверка
заключения, открытые решения и передача пунктов. Ожидание ответа человека не
имитировать: этап подготовки вопросов завершён, реальное ожидание записывается
отдельно по [правилам монитора](pipeline-monitor.md).
`calls.jsonl` хранит время команд и размер ответа; `session.json` хранит объём
прочитанных и повторных строк/байтов текущей попытки. Время этапа включает работу
агента и ожидания, его нельзя называть чистым временем модели.

Версии заключений и локальная подпись защищают от случайной подмены сохранённого
файла. Подпись не защищает от владельца компьютера с доступом к ключу. В одном
каталоге экспертизы ведётся одна активная попытка; параллельные задачи используют
разные каталоги. Структурный контракт не гарантирует смысловую правильность.
Данные информационной базы в ключ заключения не входят; заключение не заменяет
актуальную COM/UI-проверку и не разрешает переиспользовать её результат.
