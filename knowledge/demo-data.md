# Демоданные: откуда база → посев → проверки → сброс → перенос

Сквозная схема работы с данными для разработки и тестов. Собрана из проектов EAM, МВМ, ZHDRM, НПЦАП
(сентябрь–октябрь 2026); у каждого правила — уверенность и разбор. Сами уровни проверки — `testing.md`,
здесь — откуда берутся данные, как их сеять, сбрасывать и переносить.

```text
база (копия рабочей | пустая | .dt) → посев (идемпотентный, одна транзакция) → проверки на данных
      ↑                                                                              │
      └──────────── сброс: копия заново или очистка + повторный посев ←──────────────┘
                                         → перенос: выгрузка JSON/XDTO + сверка
```

## 1. Откуда база (HIGH)

| Источник | Когда | Чего нельзя |
|---|---|---|
| Копия рабочей базы | проверка доработки на настоящих данных, отчёты (`com reports`), заполненность | запускать посев на САМОЙ рабочей; ждать от копии «пустых окон» |
| Пустая база + конфигурация | уровень 1 (загрузка), посев с нуля, тесты с предсказуемыми данными | судить по ней о формах на данных (`testing.md` §5) |
| `.dt` (чужой или боевой) | старт проекта, перенос | забывать, что пользователи в нём боевые |

- **Что.** Боевой `.dt` и копия рабочей базы несут настоящих пользователей и данные: демо-посев и массовые правки — только
  на копии; факт записать в AGENTS.md проекта сразу. **Почему.** Посевы находят и перезаполняют объекты по меткам —
  совпадение метки в боевых данных испортит их. `new-project.md` §1 п.3, `deployment.md` §7; МВМ —
  `reference/source-project-CLAUDE.md` (рабочая база «МВМ локальная»).
- **Копию «живой» базы приводить к состоянию «после посева».** Копия приносит свежие данные обмена: тесты, ждавшие
  пустые окна, падают разом. Очистить оперативные регистры, предусловия теста — явно в самом тесте. Копию `1Cv8.1CD`
  снимать, когда её никто не пишет (Apache с регламентными заданиями остановлен). Case 077 (дополнение ZHDRM).
- **`.dt` помнит версию платформы** (8.5.1 → только 8.5.1+); `CREATEINFOBASE` и `/RestoreIB` — одной версией.
  `/UpdateDBCfg` копии применяет и чужие отложенные изменения структуры — сначала отдельный прогон и журнал. Case 080 §1, §5.

## 2. Посев: принципы

**Идемпотентность по метке (HIGH, МВМ).** Каждый созданный объект несёт метку (в комментарии, коде или отдельном
реквизите): повторный посев НАХОДИТ свои объекты и перезаполняет их, а не плодит. На МВМ листы и путевые листы демо-набора
находятся по метке в комментарии; заявки — по номерам `ДЕМО-21…27`. Справочники без метки ищутся по естественному
ключу (наименование, госномер). `reference/source-project-CLAUDE.md` (демо-набор АРМ водителя); общий принцип —
`generators.md` (идемпотентность).

**Одна транзакция, очистка — до неё (MEDIUM, МВМ).** Посев целиком в `НачатьТранзакцию … ЗафиксироватьТранзакцию`:
упал на середине — база как была, повторный запуск не встречает полупосев. Чистку чужих и старых данных (удаление,
отмена проведения) вести ДО транзакции и пропускать с причиной: проведённые документы копии типовая может не дать
перепровести, и одна такая ошибка откатит весь посев. `testing.md` §7.

**Отчёт о пропусках с причиной (HIGH).** Каждый `Продолжить` в посеве — строка отчёта «что пропущено и почему»; иначе
«пометка лишних» или следующий шаг молча снимает то, что не записалось (case 044). Итог посева — счётчики по видам
объектов и список пропусков; после посева — `com fill` (`testing.md` §6): реквизит, пустой у ВСЕХ объектов, — пробел
посева (на EAM ~100 таких и один автор у всех документов).

**Посев проводит цепочки как пользователь (HIGH).** Заказ → акт → списание, основной → корректировочный: такой посев —
интеграционный тест (уровень 7). Он нашёл регистр, в который два документа пишут один ключ (case 064), запрос к
справочнику без кода (case 065). После посева — отчёты на данных (`com reports`) и заполненность.

**«Сейчас» и даты (MEDIUM).** Демо считается от момента посева: «выполнен» — в прошлом, «в пути» — сейчас, «три впереди» —
в будущем (МВМ: семь рейсов в разных состояниях, путевые листы «на сегодня»). Через COM нет `ДобавитьМесяц` и части
глобального контекста — даты считать в Python и передавать готовыми (`testing.md` §3). Отчёты, обрезающие период текущим
моментом, сравнивать на конце периода в прошлом — иначе результат зависит от времени запуска (case 082 §6).

**Ловушки сценария на копии (HIGH, МВМ, `testing.md` §7).** Начальная страница пользователя может быть пустой — форму
сценария открывать параметром `/C`, а не надеяться на АРМ; автоматика на копии рабочей базы выбирает из всего
настоящего парка — демо-объектам задавать свойства, которые ведут выбор к демо-данным.

## 3. Где хранить посев

| Вариант | Плюсы | Минусы | Где было |
|---|---|---|---|
| Общий модуль конфигурации (серверный, экспорт) + кнопка в АРМ | одна транзакция на сервере, вызывается и пользователем, и `platform.py <json> com call Модуль.Функция`; виден в git вместе с объектами | попадает в поставку — в бою кнопку прятать по роли/константе | МВМ (кнопка посева в АРМ диспетчера) |
| Python через COM (`cn.NewObject`, запись объектов из скрипта) | не трогает конфигурацию, удобно считать даты и читать JSON | транзакция и ошибки — через COM, медленнее на тысячах объектов, нет глобального контекста | ZHDRM (`демо_база.py`: `посеять(cn)`, поиск по наименованию), НПЦАП (перенос, case 082) |
| Обработка внутри конфигурации КОПИИ, `/URL e1cib/app/Обработка.<Имя>` | нет «Предупреждения безопасности», рабочая база не меняется | только для копии, не для повторного прогона в разработке | case 080 §3 (выгрузка) |

Совет (MEDIUM): логика посева — в общем модуле (её же проверяет `com call`), а Python только запускает, передаёт даты и
печатает отчёт. Длинные сценарии — клиентом по `/C` с журналом в `ЖурналРегистрации` (`testing.md` §7). Структуру
параметров для `com call` собирать `cn.NewObject("Структура")` (`testing.md` §3).

## 4. Безопасность (HIGH)

- Не на боевой базе: проверка в самом посеве (константа «демо-режим», имя базы, пустой список боевых пользователей) — LOW,
  не проверено как общий приём; в наборе принято правило процесса (`deployment.md` §7).
- Без реальных персональных данных: демо-водитель «Смирнов», машина «Н453РУ190» — выдуманные.
- Паролей ИБ-пользователей демо в коде и наборе нет (в `reference/` вычищены); пароль задаёт пользователь. Копия с
  «Администратором» без пароля — не открывать в сеть (case 077, «Безопасность»).
- Выгрузка чужой базы — без паролей и ключей: реквизиты с «пароль» в имени не выгружаются, в отчёт — факт и место, без
  значений (case 080 §4, §6).

## 5. Сброс и повторный посев

- Быстрее всего — свежая копия рабочей (`песочница` в проектах без EDT) или новая пустая база + повторный посев (HIGH: так
  работают ZHDRM и УП; время не замерялось).
- Повторный посев в той же базе — по меткам (§2) перезаполняет свои объекты; чужие данные, мешающие тесту, чистить до
  транзакции (MEDIUM).
- Откат через `/RestoreIB` эталонного `.dt` — работает, но медленнее копии каталога (LOW, замеров нет).

## 6. Перенос данных между базами (HIGH, cases 080, 082)

- **Выгрузка в JSON** (case 080 §4): обход справочников, документов, регистров сведений, констант; ссылка —
  `{ref, type}`, даты — `XMLСтрока` без зоны, `ХранилищеЗначения` пропускается, табличные части — `_tables`, файл на
  объект метаданных + `_журнал.json` со счётчиками.
- **XDTO с сохранением ссылок** (case 082 §2): `cn.XDTOSerializer`, запись в режиме `ОбменДанными.Загрузка` —
  проведённые остаются проведёнными; предопределённые расширения создаются со своими ссылками — убрать их перед записью.
- **Сверка обязательна** (case 082 §4): тем же снимком в новой базе, по ссылкам, не по порядку; плюс отчёты до/после
  на одних данных и перепроведение нескольких документов. Итог НПЦАП — 0 расхождений.

## Чего в наборе нет (LOW / не проверено)

- Образца общего модуля посева в `examples/` нет — посевы проектов не перенесены (МВМ `демо_данные_1с.py`, ZHDRM
  `демо_база.py` лежат в своих репозиториях).
- Посев на серверной базе (`Srvr=`), посев больших объёмов (десятки тысяч документов) и его время — не замерялись.
- Обезличивание копии боевой базы (замена ФИО, телефонов) — не делалось.
- Автоматическая защита «не на боевой» внутри посева — см. §4, принято только правилом процесса.
