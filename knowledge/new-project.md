# Новый проект доработок: старт с нуля из выгрузки `.dt`

Порядок, отработанный на проекте-источнике (HIGH, кроме отмеченного). Цель —
через час иметь проект EDT под git, справочник метаданных конфигурации,
память проекта для Claude, проверки и резервную копию на GitHub, и только
потом первый объект.

## 1. База из `.dt`

1. Создать пустую информационную базу (файловую для разработки достаточно;
   на сервере — если так будет и в бою).
2. Конфигуратор → Администрирование → Загрузить информационную базу → `.dt`.
   Запустить в режиме предприятия один раз: типовая выполнит первоначальное
   заполнение и обновление ИБ (это может занять минуты).
3. Если `.dt` боевой — пользователи в ней боевые: демо-посевы и массовые
   правки только на копии. Сразу записать это в CLAUDE.md проекта.

## 2. Проект EDT из базы

1. EDT → File → Import → «Импорт конфигурации из информационной базы»
   (1C:Enterprise → Configuration from infobase). Имя проекта — короткое,
   латиницей или кириллицей без пробелов; версия платформы — та, на которой
   собрана конфигурация (у неё же берётся и режим совместимости).
2. Дождаться полного импорта (десятки минут на большой типовой) и построения
   проекта; Problems типовой обычно не пуст — это норма, свои ошибки
   отличают по префиксу.
3. Привязать проект к базе (Infobases → добавить → сопоставить) и включить
   «Обновлять конфигурацию ИБ автоматически» — иначе каждую укладку придётся
   подтверждать руками.

## 3. Git и резервная копия

```bash
git config --global core.autocrlf false        # файлы EDT — побайтово
cd <проект EDT> && git init && git add -A && git commit -m "Конфигурация поставщика как есть"
```

Бинарник поставщика `src/Configuration/ParentConfigurations/*.cf` — в
`.gitignore` (сотни МБ, не диффится); шаблон — `bootstrap/gitignore.edt`.
Первый коммит — ДО любых доработок: он и есть точка сравнения «что наше».

## 4. Стартовый набор

```bash
python <skill>/tools/new_project.py <проект EDT> <папка инструментов> --prefix <префикс> --name "Название"
```

Делает: справочник метаданных из `.mdo` (`метаданные/объекты.md`,
`метаданные/реквизиты.csv` — grep по нему заменяет память модели о полях),
`CLAUDE.md` проекта из шаблона (`bootstrap/CLAUDE.md.template`), `.gitignore`
обеих папок, `инструменты/отправить_всё.py` для резервной копии, первый прогон
`check_project` по префиксу, `.claude/settings.json` с хуком `tools/hook_heredoc.py`. Существующие файлы
не трогает.

**Хук Claude Code (case 092).** Heredoc с обратной косой чертой (`python - <<'EOF'` с `\n`, `\d` в коде) в Git Bash
ломается раз за разом, и правило в CLAUDE.md этого не останавливает. PreToolUse-хук отклоняет такую команду с
подсказкой «Write + python файл.py». Проект без EDT (выгрузка Конфигуратора) — карта `python tools/config_map.py <выгрузка> [подсистема …] --итог КАРТА.md` (ссылку на неё — в CLAUDE.md проекта: «перед правкой — раздел объекта в КАРТА.md») и только хук:
`python <skill>/tools/new_project.py --hook <папка проекта>`.

Затем:

```bash
cd <папка инструментов> && git init && git add -A && git commit -m "Стартовый набор"
gh repo create <имя>-tools --private && gh repo create <имя>-edt --private
python инструменты/отправить_всё.py --tools <url> --edt <url>
```

## 5. Память проекта

`CLAUDE.md` из шаблона содержит только общие правила; в первый же день
дописать: для кого проект и что решает, версия платформы/EDT, имя базы и
публикация, что боевое. Раздел «Ловушки» пуст намеренно — он растёт от
реальных ошибок, и каждая общая ловушка одновременно становится кейсом в
наборе знаний (`cases/`), а не только строкой в CLAUDE.md.

## 6. Первый объект

Не с нуля, а по образцу: `tools/scaffold.py <EDT> catalog ПримерСправочник
<Префикс>Имя` копирует рабочий пример с переименованием и uuid5, затем
`check_project --prefix`. Первое обновление базы — ПОЛНОЕ (новые объекты),
дальше инкрементальное. Новый объект — в подсистему и в справку тем же
коммитом (`knowledge/subsystems-and-ui.md`).

## 7. Что переносить из старого проекта, а что нет

- **Переносится**: набор знаний (уже подключён), техника генераторов
  (`reference/generators/` как образец: идемпотентные шаги с якорями по
  содержимому, проверки перед укладкой), скрипт резервной копии, правило
  «объект — в подсистему и в справку», порядок замера производительности.
- **Не переносится**: генераторы старого проекта как код (в них зашита его
  спецификация), его `CLAUDE.md` целиком (предметные ловушки не нужны, общие
  уже в наборе), справочник метаданных старой конфигурации.

Что не проверялось (LOW): импорт из базы на серверной СУБД и конфигурации
с расширениями (`.cfe`) — там могут быть свои шаги.
