# Единый цикл проекта без EDT

`tools/project_cli.py` работает с явным JSON проекта и только с `test_ib`.
Он не меняет GitHub и не устанавливает платформу. Исходники защищаются
FrozenRun; рабочие файлы и резервная копия остаются в `.platform/runs/<id>`.

Минимальные настройки: `format: designer`, `configuration_kind: own`, `dump`,
`v8`, `test_ib`, `metadata_version`, `compatibility_mode`, `work`, `test_usr`.
Пути относительны JSON. `production_ib`, если задан, должен отличаться от test_ib.
Рабочий каталог и тестовая база не могут находиться внутри дерева исходников.
Платформа и отдельная тестовая база должны уже существовать; для собственной
пустой песочницы есть `tests/designer/create_fixture.py`.

Команды, где `<json>` — настройки конкретного проекта:

```
python tools/project_cli.py doctor --config <json>
python tools/project_cli.py lint --config <json>
python tools/project_cli.py check --config <json>
python tools/project_cli.py test --config <json>
python tools/project_cli.py release --config <json>
```

doctor читает доступность Python, зависимостей, COM, платформы и экрана. Наличие
экрана не доказывает видимость окна; каждый снимок проверяется отдельно.
lint проверяет вход, XML и BSL; baseline v2 различает контекст и количество
ошибок. Старый текстовый baseline читается с ограниченным количеством записей.
Перезаписывать его через `--remember` можно только после изучения унаследованных
дефектов; новую ошибку нельзя скрывать обновлением baseline.

check: структура → линт → резервная копия тестовой базы (DumpIB) → загрузка →
UpdateDBCfg → CheckModules → обратная выгрузка → сверка. Неизвестная ошибка
или отличие останавливают цикл; исходники автоматически не перезаписываются.
ConfigDumpInfo.xml — служебный индекс, исключён из сравнения; значимые XML/BSL
сравниваются. Косметика учитывает BOM/CRLF и отступы между XML-элементами,
сохраняет текст листьев и объявления пространств имён.

test дополнительно выполняет `com_test` (Python-скрипт проекта) и `ui_scenario`.
COM-скрипт получает ONECODEX_TEST_IB и ONECODEX_ARTIFACT, использует только
тестовую базу. Секреты задаёт отдельный проектный адаптер, не публичный JSON.
UI создаёт собственные процессы; завершает только их, хранит run_id, manifest,
журнал и кадры. Старые кадры не считаются текущим результатом.

release повторяет полный цикл, требует COM и UI по умолчанию и выпускает CF
или EPF в `release_target` через атомарную замену с контролем исходников.
`required_test_levels` меняется только по явной области приёмки проекта.
Это локальный артефакт, не обновление рабочей базы и не публикация репозитория.

Типы: own — полная загрузка своей конфигурации; vendor — обязательный список
`load_files` при полной исходной выгрузке, сохраняющей поддержку и Ext;
extension — требуется `extension`; external — один корневой XML EPF.
EPF собирается и обратно выгружается; компиляцию её модуля подтверждает COM/UI,
а не общий CheckModules базы. ERF пока не поддержан командой release.

`check_modes` задаёт режимы компиляции; по умолчанию тонкий клиент, сервер,
внешнее соединение. Веб-клиент и SQL требуют отдельной приёмки.
Форматы 2.20 и 2.21 выбираются через `with designer_lib.generation_context(...)`;
старый VERSION оставлен для совместимости, новые генераторы его не меняют.
