# Выбор проверок и продолжение выпуска

Модули `tools/workflow/verification.py` и `watchdog.py` не подключаются к базе
самостоятельно. Проектный адаптер задаёт полномочия, изолированную тестовую базу,
актуальные идентификаторы окружения и реальные операции платформы. Ускорение
проверяется на одинаковых входах; наличие кэша само по себе не доказывает ускорение.

## Проверки по изменениям

```python
from tools.workflow.verification import TestSpec, select_tests, VerificationCache

tests = [TestSpec('section', 'tests/section.py',
                  ('source/Catalogs/Sections/**', 'source/CommonModules/Methodology/**'))]
selected = select_tests(changed_files, tests, ignored_patterns=('reports/*',))
cache = VerificationCache(project)
```

`dependencies` — явные проектные glob-пути; скрипт теста добавляется всегда.
Общий модуль указывается во всех зависящих тестах. Неизвестная зависимость
(`None`) или нераспознанный изменённый файл выбирают весь набор. Исключения
для отчётов задаются явно: инструмент не выводит их из расширения `.md`.

Контекст содержит непустые короткие идентификаторы `source`, `environment`,
`database`, `configuration`, `schema`, `data`, `revision`, `dataset`.
`source` — хеш фактических исходников. `revision` включает версию исполняемых
скриптов и плана проверки, не только Git HEAD; незакоммиченная правка теста
также меняет его содержательный хеш. `database` — идентификатор конкретной ИБ,
`schema` и `data` — актуальные свидетельства состояния, полученные адаптером.
Строки подключения, пароли и аргументы команд в контекст не передаются.

`cache.record(spec, context, ['.platform/evidence/result.json'])` сохраняет
успешный результат со SHA256 входов, скрипта и файлов доказательств.
`status='failed'` отменяет прежний успех. `can_reuse(spec, context)` возвращает
ложь при изменении контекста, скрипта, зависимостей, доказательств или подписи.
Если адаптер не может подтвердить актуальность данных/схемы ИБ, кэш не применяется.

Файлы кэша и локальный ключ находятся в `.platform/verification`, вне Git.
HMAC обнаруживает подмену записи без локального ключа и случайное повреждение.
Это не граница полномочий против владельца всей рабочей папки. Параллельные
операции одного проекта должны держать существующий `project_lock`.

## Продолжение выпуска

```python
from tools.workflow.verification import ReleaseSession

session = ReleaseSession(project, 'release-id', read_current_context)
session.run('backup', create_backup, evidence=['.platform/backup/verified.json'], backup=True)
session.run('check', check_modules, evidence=['.platform/check/result.json'])
session.finish(final_integrity)
# После успеха — existing_frozen_run.publish(), который повторно проверяет входы.
```

Используется только непрерывный префикс успешных этапов с неизменными
контекстом и доказательствами. Перед выполнением callback записывается
`running`: авария не оставляет прежний успешный результат. Возраст проверенной
резервной копии ограничен `max_backup_age` (по умолчанию 3600 с). Изменение
базы, данных, схемы, исходника, окружения или скриптов требует нового выполнения.

Для операции, закономерно меняющей состояние (например, загрузка конфигурации),
адаптер передаёт `expected_after` с заранее ожидаемым контекстом. Любая другая
мутация после callback отклоняет результат. Контекст перечитывается между
этапами. Даже полностью повторно используемый префикс требует нового вызова
`finish(final_integrity)` и свежего проверенного резерва.

Если безопасная проверка закономерно меняет физический хеш файла ИБ (например,
CheckModules записывает служебный кэш), можно явно передать
`transition(before, after) -> True`. Этот режим разрешает изменение только
`data`; source/environment/database/configuration/schema/revision/dataset и
любые дополнительные поля обязаны совпадать. Он несовместим с `expected_after`.
Адаптер должен разрешать такую политику только для подтверждённой операции
изолированной песочницы под исключительной блокировкой, а не маскировать
неизвестные прикладные записи. По умолчанию контекст остаётся строго неизменным.
В checkpoint сохраняется фактический новый хеш; при resume проверяются актуальный
контекст и политика перехода по сохранённым before/after. Валидатор получает
копии словарей и должен вернуть именно True; False/None, исключение или побочное
изменение контекста не дают успешный checkpoint. Callback самой операции
успешен только при None или целом 0; False означает ошибку.

Эта библиотека не ослабляет `FrozenRun`, не заменяет атомарную публикацию и
не разрешает обновлять рабочую базу. Доверять только существованию CF нельзя.

## Подготовка копии исходников

`FrozenRun(..., progress=callback)` сохраняет `preparation_stages`:
`hash_live`, `copy`, `verify_live`, `verify_copy`, `normalize_bsl`,
`hash_normalized`, `read_leases`, `verify_leases`. У каждого этапа есть начало,
конец, статус и длительность; в `preparation_progress` — имя и число обработанных
файлов. Промежуточное число обновляется каждые 64 файла. Имена файлов и сообщения
исключений не попадают в сигнал прогресса. Копия остаётся независимой, без hardlink;
нормализация не трогает исходник. Запрет записи Windows и проверки манифестов сохранены.

## Наблюдение за долгой операцией

```python
from tools.workflow.watchdog import Phase, run_monitored, StalledOperation

phase = Phase('CheckModules', expected_seconds=30, cancel_safe=True)
try:
    code = run_monitored(own_popen, read_progress_token, phase, on_event=report_progress)
except StalledOperation as failure:
    # Для unsafe-фазы сохранить handle и проверить безопасное завершение.
    diagnose(failure.event)
```

Прогрессом считается новый подтверждённый результат: количество скопированных
файлов, новая запись журнала выполненных действий, подтверждённый этап.
CPU, число опросов и изменение времени не подходят. По умолчанию через 60 с
без прогресса формируется предупреждение, через 120 с — остановка ожидания.
Превышение удвоенной ожидаемой длительности даёт отдельное предупреждение.
`access_denied_provider` сообщает отказ доступа сразу, не ожидая таймера.

Произвольный PID не принимается: нужен созданный задачей `subprocess.Popen`.
При `cancel_safe=True` вызывается `terminate()` только этого процесса с
ограниченным ожиданием; дерево и чужие процессы не уничтожаются. Для UpdateDBCfg
и других потенциально опасных фаз `cancel_safe=False`: процесс не останавливается,
выбрасывается `StalledOperation(kind='stalled_unsafe')`, требуется диагностика
безопасного завершения. Адаптер не должен затем безусловно убивать процесс в finally.

`RetryGate` запрещает повтор одинаковой ошибки при неизменном отпечатке условий.
Новый отпечаток должен означать фактическое исправление прав, входов или среды,
а не новое имя попытки. Инструмент не подтверждает эти условия вместо адаптера.
