# 1C:EDT Project Storage Guide

## Назначение

Этот документ описывает правила анализа и изменения файлового представления конфигурации 1С в проекте **1C:Enterprise Development Tools (1C:EDT)**.

Документ предназначен прежде всего для Claude Code и других автоматизированных инструментов разработки.

Для данного проекта источником истины является:

```text
./src
```

Это **внутреннее файловое представление проекта EDT**, а не XML-выгрузка Конфигуратора.

---

# 1. Главная архитектурная модель

Нельзя воспринимать EDT-проект как просто набор независимых XML-файлов.

Правильная модель:

```text
Файлы проекта
        │
        ▼
сериализация EDT
        │
        ▼
Big Model / EMF models
        │
        ├── модель метаданных
        ├── модель форм
        ├── модель СКД
        ├── модель прав
        └── другие модели
        │
        ▼
семантические индексы EDT
        │
        ▼
валидация / сборка / экспорт в 1С
```

Для BSL действует отдельная цепочка:

```text
Module.bsl
    │
    ▼
парсер Xtext
    │
    ▼
AST / semantic model BSL
    │
    ▼
проверки EDT
```

Файл является первичным текстовым представлением BSL.

Для метаданных ситуация обратная: физический файл является сериализованным представлением объектной модели EDT.

---

# 2. Критически важное различие: EDT ≠ Configurator XML

Старый формат разработки:

```text
Configuration.xml
Catalogs/*.xml
Documents/*.xml
ConfigDumpInfo.xml
```

являлся XML-выгрузкой Конфигуратора.

Файлы EDT:

```text
*.mdo
*.form
*.rights
*.dcs
*.dcss
*.dcssca
*.mxlx
*.cmi
*.cai
*.hpwa
```

являются другим представлением.

Нельзя:

- применять к `.mdo` XSD или правила XML-выгрузки Конфигуратора;
- копировать XML-фрагменты из старой выгрузки непосредственно в `.mdo`;
- предполагать одинаковую структуру ссылок;
- предполагать одинаковое представление UUID;
- предполагать одинаковую организацию форм;
- использовать `ConfigDumpInfo.xml` как индекс EDT-проекта.

---

# 3. Уровни стабильности

При работе с EDT различать три уровня.

## Уровень A — стабильный интерфейс разработки

К нему относятся:

- объектная модель EDT;
- API EDT;
- Big Model Framework;
- сервисы EDT;
- семантическая модель BSL;
- команды EDT CLI.

Именно этот уровень предпочтителен для автоматизации.

---

## Уровень B — файловое представление EDT

Например:

```text
Catalog.mdo
Document.mdo
Form.form
Rights.rights
```

Формат достаточно детерминирован, чтобы:

- анализировать его;
- сравнивать через Git;
- находить свойства;
- иногда выполнять локальные изменения.

Однако его нельзя считать стабильным публичным API.

Версия хранения EDT может изменяться.

---

## Уровень C — внутренние детали сериализации

Например:

- порядок XML-узлов;
- omission/default rules;
- внутренние идентификаторы;
- служебные ссылки;
- правила разбиения объекта по нескольким файлам;
- внутренние namespace;
- оптимизация хранения.

Нельзя строить бизнес-логику автоматизации на предположении, что такие детали неизменны между версиями EDT.

---

# 4. Версия файлового представления проекта

В проекте существует файл:

```text
DT-INF/PROJECT.PMF
```

Он описывает технические параметры проекта EDT.

При анализе нового проекта сначала читать этот файл.

В нём могут присутствовать сведения:

```text
Manifest-Version
Runtime-Version
Store-Version
Product-Version
Require-Configuration
Base-Project
```

Особенно важен:

```text
Store-Version
```

Это версия формата resource store проекта EDT.

Следствие:

**нельзя считать файл `.mdo`, созданный одной версией EDT, абсолютно идентичным по требованиям сериализации другой версии EDT.**

Не изменять `PROJECT.PMF` вручную.

---

# 5. Корень исходников

Основные исходники:

```text
src/
```

Тип объекта определяется прежде всего каталогом первого уровня.

Например:

```text
src/Catalogs/
src/Documents/
src/CommonModules/
src/InformationRegisters/
src/AccumulationRegisters/
src/Reports/
src/DataProcessors/
```

Пример логического соответствия:

```text
src/Documents/Заказ/
```

соответствует:

```text
Документ.Заказ
```

---

# 6. Полные имена объектов — FQN

При поиске ссылок необходимо мыслить не только именем файла, но и полным именем объекта.

Примеры:

```text
Catalog.Номенклатура
Document.Заказ
InformationRegister.Цены
CommonModule.ОбщегоНазначения
```

В модели EDT такие имена являются важным механизмом идентификации и разрешения ссылок.

Поэтому нельзя предполагать, что текстовая ссылка определяется только:

```text
Номенклатура
```

Нужно учитывать класс объекта:

```text
Catalog.Номенклатура
```

---

# 7. UUID

UUID метаданных являются идентификаторами модели.

Правила:

## Существующий объект

Никогда не изменять UUID существующего объекта без специальной причины.

Запрещено:

- регенерировать UUID;
- заменять UUID случайным;
- копировать UUID другого объекта;
- менять UUID при переименовании.

---

## Новый объект

При создании нового объекта новый UUID может требоваться.

Но генерация UUID — это только часть создания объекта.

Необходимо также учитывать:

- containment;
- ссылки;
- FQN;
- родительскую коллекцию;
- external properties;
- дополнительные файлы объекта.

Поэтому наличие валидного UUID само по себе не означает, что объект корректен.

---

# 8. Containment — вложенные объекты

Многие объекты метаданных физически являются частью родительского объекта.

Например документ логически содержит:

```text
Document
├── Attributes
├── TabularSections
│   └── Attributes
├── Forms
├── Commands
└── Templates
```

Справочник:

```text
Catalog
├── Attributes
├── TabularSections
├── Forms
├── Commands
└── Templates
```

Регистр:

```text
Register
├── Dimensions
├── Resources
├── Attributes
├── Forms
└── Commands
```

При добавлении вложенного объекта недостаточно создать произвольный XML-узел.

Нужно сохранить модель containment EDT.

---

# 9. `.mdo`

`.mdo` — основное сериализованное описание объекта метаданных EDT.

Примеры:

```text
src/Documents/Заказ/Заказ.mdo
src/Catalogs/Номенклатура/Номенклатура.mdo
src/CommonModules/ОбщегоНазначения/ОбщегоНазначения.mdo
```

Файл может описывать:

- класс объекта;
- UUID;
- имя;
- синоним;
- свойства объекта;
- типы;
- вложенные объекты;
- ссылки на другие метаданные;
- свойства, специфичные для класса объекта.

---

# 10. `.mdo`: способ чтения

Claude может свободно читать `.mdo`.

При анализе объекта:

1. Найти его `.mdo`.
2. Определить класс объекта.
3. Определить имя и UUID.
4. Изучить свойства.
5. Определить вложенные объекты.
6. Найти ссылки на внешние свойства.
7. Посмотреть директории `Forms`, `Templates` и другие.
8. Найти BSL-модули объекта.

---

# 11. `.mdo`: способ изменения

Уровень риска:

**средний — высокий.**

Разрешены только локальные изменения, структура которых однозначно понятна на основании:

- текущего файла;
- нескольких аналогичных объектов текущего проекта;
- модели EDT;
- последующей validation.

Пример относительно простого изменения:

```text
изменение существующего текстового свойства
```

значительно безопаснее, чем:

```text
создание нового реквизита
```

а создание нового объекта метаданных ещё сложнее.

---

# 12. Справочники

Физически:

```text
src/Catalogs/<Имя>/
```

Логическая модель:

```text
Catalog
├── основные свойства
├── Attributes
├── TabularSections
├── Forms
├── Templates
└── Commands
```

Типичные BSL:

```text
ObjectModule.bsl
ManagerModule.bsl
```

и BSL форм.

При изменении реквизита учитывать:

- имя;
- UUID;
- тип;
- составной тип;
- квалификаторы типа;
- историю данных;
- индексирование;
- использование в формах;
- использование в коде;
- возможную реструктуризацию БД.

---

# 13. Документы

Физически:

```text
src/Documents/<Имя>/
```

Логическая модель:

```text
Document
├── Attributes
├── TabularSections
├── Forms
├── Templates
├── Commands
├── posting properties
└── register records
```

Типичные модули:

```text
ObjectModule.bsl
ManagerModule.bsl
```

При работе с документом дополнительно проверять:

- проведение;
- движения;
- регистры;
- оперативное проведение;
- нумератор;
- периодичность номера;
- привилегированный режим;
- подписки на события.

---

# 14. Регистры сведений

Физически:

```text
src/InformationRegisters/<Имя>/
```

Логическая структура:

```text
InformationRegister
├── Dimensions
├── Resources
├── Attributes
├── Forms
└── Commands
```

Особенно важны:

- периодичность;
- режим записи;
- ведущие измерения;
- типы измерений;
- состав ключа.

Изменение состава измерений может менять физическую структуру хранения данных.

---

# 15. Регистры накопления

Физически:

```text
src/AccumulationRegisters/<Имя>/
```

Логическая структура:

```text
AccumulationRegister
├── Dimensions
├── Resources
├── Attributes
├── Forms
└── Commands
```

Обязательно учитывать:

```text
ВидРегистра = Остатки / Обороты
```

и использование виртуальных таблиц:

```text
Остатки
Обороты
ОстаткиИОбороты
```

Изменение измерения или ресурса — структурная операция высокой опасности.

---

# 16. Общие модули

Физически:

```text
src/CommonModules/<Имя>/
```

Основной код:

```text
Module.bsl
```

Описание свойств самого модуля:

```text
<Имя>.mdo
```

В `.mdo` важны свойства исполнения:

- server;
- client;
- external connection;
- server call;
- global;
- privileged;
- reuse return values и другие.

Поэтому при переносе процедуры между общими модулями нельзя анализировать только BSL.

Нужно также читать `.mdo` обоих модулей.

---

# 17. `.bsl`

`.bsl` является текстовым исходником встроенного языка.

Это наиболее безопасный формат для прямого изменения Claude Code.

Разрешено:

```text
read
search
edit
diff
```

без промежуточного XML.

---

# 18. Важная особенность BSL-модели EDT

EDT строит семантическую модель BSL из текста.

Не считать, что существует отдельная сериализуемая AST, которую нужно править вместо файла.

Рабочая операция:

```text
редактировать Module.bsl
        ↓
EDT перечитывает
        ↓
строит модель
        ↓
выполняет проверки
```

---

# 19. Модули объекта

В зависимости от класса объекта могут существовать:

```text
ObjectModule.bsl
ManagerModule.bsl
RecordSetModule.bsl
Module.bsl
```

Нельзя определять назначение модуля только по имени процедуры.

Всегда учитывать тип файла.

---

# 20. Формы

Форма состоит как минимум из двух разных частей:

```text
Form.form
Module.bsl
```

Пример:

```text
Forms/ФормаДокумента/
├── Form.form
└── Module.bsl
```

`Module.bsl` можно редактировать как обычный BSL.

`Form.form` относится к отдельной модели форм EDT.

---

# 21. Модель `Form.form`

Форма концептуально содержит:

```text
Form
├── Attributes / Fields
├── Items
├── Commands
├── Handlers
├── Form events
├── data bindings
├── DataPath
├── ExtInfo
└── presentation properties
```

Типичные важные элементы:

```text
items
fields
commands
handlers
dataPath
segments
extInfo
```

Элементы формы имеют собственные идентификаторы.

Нельзя:

- произвольно дублировать id;
- менять id существующих элементов;
- перемещать XML-узлы без понимания containment;
- создавать DataPath без проверки существования пути.

---

# 22. DataPath формы

Пример логического пути:

```text
Объект.Контрагент
```

или:

```text
Объект.Товары.Номенклатура
```

В EDT такой путь сериализуется не обязательно так же, как в XML Конфигуратора.

Нужно анализировать модель `form:DataPath` и её `segments`.

После изменения формы обязательно проверять:

1. EDT validation.
2. Открытие формы в EDT.
3. Синхронизацию в тестовую ИБ.
4. Фактическое открытие формы в 1С.

---

# 23. `Form.form` имеет очень высокий риск ручного изменения

Формы содержат большое количество взаимосвязанных данных:

```text
element ID
command
data source
DataPath
handler
context menu
tooltip
ExtInfo
```

Поэтому предпочтительный порядок:

```text
EDT API / MCP
       ↓
model Form
       ↓
EDT serialization
```

а не:

```text
Claude генерирует Form.form с нуля
```

---

# 24. Роли

Роль является объектом метаданных.

Файлы обычно разделяют:

```text
описание роли
+
Rights.rights
```

`Rights.rights` содержит права объектов.

Концептуально:

```text
Role
└── Rights
    ├── Object/FQN
    │   ├── Read
    │   ├── View
    │   ├── Edit
    │   └── ...
    └── ...
```

---

# 25. `Rights.rights`

Риск:

**очень высокий.**

Причина:

ошибка может быть XML-корректной, но семантически изменить права доступа.

Правила:

- не выполнять массовое редактирование;
- не добавлять право по догадке;
- обязательно проверять FQN объекта;
- сравнивать с аналогичной ролью;
- валидировать через EDT;
- функционально проверять пользователя с этой ролью.

---

# 26. СКД

Файлы семейства:

```text
*.dcs
*.dcss
*.dcssca
```

относятся к системе компоновки данных и её настройкам.

Логическая модель схемы компоновки включает:

```text
DataCompositionSchema
├── DataSources
├── DataSets
├── DataSetLinks
├── CalculatedFields
├── TotalFields
├── Parameters
├── NestedSchemas
├── Templates
├── DefaultSettings
└── SettingsVariants
```

Это отдельная сложная модель.

---

# 27. Изменение СКД

Риск:

**высокий.**

Можно безопасно:

- читать;
- искать запрос;
- анализировать поля;
- анализировать параметры.

Ручное структурное изменение требует:

- понимания модели DCS;
- анализа аналога;
- EDT validation;
- запуска отчёта.

Не генерировать сложную СКД с нуля прямым XML без специального инструмента.

---

# 28. Табличные документы и макеты

Файлы:

```text
*.mxlx
```

и другие файлы макетов содержат специализированные сериализованные модели.

Не применять обычное текстовое редактирование, кроме случаев, когда формат и изменение полностью понятны.

Предпочитать:

```text
EDT editor
или
EDT API
```

---

# 29. Command Interface

В проекте могут встречаться:

```text
*.cmi
*.cai
*.hpwa
```

Они связаны с интерфейсом приложения, командным интерфейсом и рабочими областями.

Риск:

**высокий.**

По умолчанию:

```text
READ ONLY FOR CLAUDE
```

если пользователь явно не поставил задачу изменить соответствующий интерфейс.

---

# 30. Основная конфигурация

Каталог:

```text
src/Configuration/
```

содержит описание самой конфигурации.

Здесь находятся свойства уровня конфигурации:

- имя;
- синоним;
- поставщик;
- версия;
- режим совместимости;
- основной интерфейс;
- языки;
- другие глобальные настройки.

Менять крайне осторожно.

---

# 31. Типы значений

Тип в модели EDT нельзя считать простой строкой.

Например:

```text
CatalogRef.Номенклатура
```

может быть частью сложного `TypeDescription`.

Тип может содержать:

- один тип;
- несколько типов;
- квалификатор строки;
- квалификатор числа;
- квалификатор даты.

При добавлении реквизита нельзя копировать только текст имени типа.

Нужно копировать структуру типа аналогичного реквизита.

---

# 32. Составные типы

Особая осторожность:

```text
Строка + СправочникСсылка.X + ДокументСсылка.Y
```

Не предполагать, что порядок или сериализация элементов составного типа не имеет значения для EDT.

Для структурного изменения предпочтительно использовать модель EDT.

---

# 33. Предопределённые элементы

Предопределённые элементы справочников, перечислений и других объектов также являются частью модели.

Не:

- менять UUID;
- менять внутреннюю идентичность;
- копировать элементы между объектами текстовым copy/paste.

Переименование предопределённого элемента потенциально влияет на код.

Искать обращения вида:

```bsl
ПредопределенноеЗначение(...)
```

и другие способы использования.

---

# 34. Перечисления

Физически:

```text
src/Enums/<Имя>/
```

Логически:

```text
Enum
└── EnumValues
```

Значение перечисления — отдельный объект модели.

Добавление значения должно сохранять:

- имя;
- UUID;
- порядок;
- синоним.

---

# 35. Подсистемы

Физически:

```text
src/Subsystems/
```

Изменение подсистемы влияет на:

- дерево функций;
- командный интерфейс;
- принадлежность метаданных;
- видимость функциональности.

Не считать подсистему просто папкой.

# 44. Алгоритм изменения BSL

Для `.bsl`:

```text
1. git status
2. найти модуль
3. найти связанные процедуры
4. найти вызовы
5. изменить минимальное количество строк
6. сохранить
7. git diff
8. EDT validation
9. функциональный тест при необходимости
```

Прямое редактирование разрешено.

---

# 45. Алгоритм изменения существующего `.mdo`

```text
1. git status

2. найти объект

3. прочитать его .mdo

4. прочитать структуру аналогичных объектов
   минимум 2 примера, если формат свойства неизвестен

5. определить соответствующий объект/feature модели EDT

6. определить, можно ли выполнить изменение через EDT API/MCP

7. если можно:
       использовать модель EDT

8. если нельзя:
       выполнить только минимальное текстовое изменение

9. не менять UUID существующих объектов

10. git diff

11. открыть/refresh проект EDT

12. выполнить validation

13. проверить синхронизацию в тестовую ИБ
```

---

# 46. Алгоритм добавления реквизита

Добавление реквизита считать структурным изменением.

```text
properties
```

После создания:

```text
EDT model validation
        ↓
update test DB
        ↓
DB restructuring
        ↓

```

Предпочтительный путь:

```text
EDT API/MCP
```

а не прямое редактирование `.mdo`.

# 47. Алгоритм изменения формы

```text
1. прочитать Form.form
2. прочитать Module.bsl
3. понять текущий DataPath
4. определить нужные form attributes
5. определить элемент-контейнер
6. определить существующие IDs
7. определить команды/обработчики
8. предпочтительно изменить модель через EDT
9. git diff
10. EDT validation
11. открыть форму в редакторе EDT
12. обновить тестовую ИБ
13. открыть реальную форму в 1С
```

Для формы одной validation недостаточно.

---

# 48. Почему validation недостаточно

EDT validation проверяет модель проекта, но окончательный результат также зависит от:

```text
EDT serialization
        ↓
экспорт / обновление ИБ
        ↓
платформа 1С
        ↓
runtime
```

Поэтому для критических изменений нужны два уровня проверки:

```text
STATIC
EDT validation

RUNTIME
тестовая информационная база
```

---

# 49. Особое правило для форм

После изменения `Form.form` считать обязательным runtime-тест.

Даже если:

```text
EDT Problems = 0
```

это ещё не доказывает, что форма корректно перенеслась в конфигурацию платформы.

---

# 50. Правило «не угадывать»

Если Claude не знает точного значения:

```text
xsi:type
namespace
feature
reference
UUID relationship
DataPath
external-property structure
```

он не должен генерировать его по аналогии с XML Конфигуратора.

Нужно выбрать один из вариантов:

```text
1. найти аналог в текущем EDT-проекте;

2. определить через EDT API/model;

3. попросить EDT создать структуру;

4. остановить структурное изменение.
```

---

# 51. Поиск аналогов

Когда требуется понять сериализацию свойства:

первый источник:

```text
текущий проект той же версии EDT
```

Искать объект того же класса с нужным свойством.

Например, чтобы понять новый реквизит документа:

```text
найти другой Document
с реквизитом такого же типа
```

Это надёжнее старой XML-выгрузки.

---

# 52. Не копировать слишком большой фрагмент

При использовании аналога копировать только минимально необходимую семантическую структуру.

Не копировать:

- UUID;
- имена;
- ссылки;
- form element id;
- объектные FQN;
- unrelated properties.

---

# 53. Git diff как часть валидации

После структурного изменения анализировать diff отдельно от BSL.

Подозрительные признаки:

```text
изменились сотни строк вместо нескольких;
изменился порядок больших блоков;
переформатировался весь файл;
появились изменения UUID;
исчезли существующие свойства;
изменились unrelated objects;
```

При наличии таких признаков остановиться и разобраться до продолжения.

---

# 54. Массовое изменение EDT-файлов

Не использовать глобальный XML formatter.

Не использовать:

```text
prettify XML
normalize XML
sort XML
rewrite namespaces
```

для EDT-файлов.

Это создаёт огромный Git diff и может нарушить правила сериализации EDT.

---

# 55. Кодировка

Сохранять исходную:

- кодировку;
- BOM;
- line endings.

Не пересохранять все файлы проекта.

---

# 56. EDT migration

Если EDT при открытии проекта предлагает:

```text
migrate
optimize project storage
```

это отдельная техническая операция.

Не смешивать её с бизнес-изменением.

Правильно:

```text
commit before migration
        ↓
migration
        ↓
separate commit
        ↓
business changes
```

Иначе невозможно отделить массовые изменения формата от разработки.

---

# 57. Версия EDT текущего проекта

Перед операциями, зависящими от файлового формата, определить фактическую версию EDT через:

```text
DT-INF/PROJECT.PMF
```

и установленную EDT.

Не использовать инструкции по сериализации другой версии без проверки.

---

# 58. Слой model API

Для программного изменения метаданных предпочтителен API EDT.

Объекты метаданных представлены классами модели, например концептуально:

```text
Configuration
Catalog
CatalogAttribute
Document
DocumentAttribute
InformationRegister
RegisterDimension
RegisterResource
Role
CommonModule
```

Использование модели позволяет EDT:

- контролировать containment;
- поддерживать ссылки;
- учитывать model feature;
- корректно сериализовать состояние.

---

# 59. Big Model

Метаданные EDT работают на Big Model Framework.

Это означает, что объект модели имеет больше семантики, чем XML-узел.

С моделью связаны:

```text
object identity
resource
FQN
references
back references
containment
transaction
indexes
```

Поэтому прямое изменение текста файла обходит часть механизмов, которые предоставляет API EDT.

# 60. MCP

Если подключён MCP-плагин EDT и он умеет изменять данный класс объекта:

предпочитать:

```text
Claude
  ↓
MCP
  ↓
EDT model
  ↓
EDT writes resources
```

вместо:

```text

  ↓

```

Но после MCP-изменений всё равно проверять:

```text
git diff

runtime
```

# 61. MCP не отменяет Git

Даже если изменение выполнено через модель EDT, возможно изменение нескольких файлов.

Всегда анализировать Git diff.

# 64. Что считать успешным изменением

Для изменения только BSL:

```text
git diff OK
+
EDT diagnostics OK
```

обычно достаточно для статического уровня.

Для изменения metadata:

```text
git diff OK
+
EDT build/validation OK
+
sync to test DB OK
```

Для изменения формы, прав, СКД или структуры данных:

```text
git diff
+
EDT validation
+
sync
+
runtime test
```

# 65. Запрещённое утверждение

Claude не должен писать:

```text
Изменение полностью проверено и работает.
```

если фактический runtime-тест не выполнялся.

Использовать точные формулировки:

```text
Статическая проверка EDT прошла.

или

Проект синхронизирован с тестовой ИБ.

или

Функциональный сценарий X протестирован.
```

# 66. Работа с ошибкой EDT

При ошибке после raw edit:

не пытаться многократно «доправлять XML наугад».

Алгоритм:

```text
git diff
↓
определить сделанное изменение
↓
прочитать точную ошибку EDT
↓
сравнить с моделью/аналогом
↓
исправить первопричину
```

Если формат неизвестен:

```text
git restore конкретного изменения
```

и выполнить его через EDT model/UI.

---

# 67. Round-trip проверка

Для особо критичных structural changes полезен round-trip:

```text
EDT project
    ↓
sync/export
    ↓
1C platform
    ↓
проверка результата
```

Не считать файловую корректность достаточной гарантией того, что платформа получит точно ту же семантику.

---

# 68. Работа с конфигурацией на поддержке

Если объект находится на поддержке поставщика:

перед структурным изменением определить:

- разрешено ли изменение;
- является ли объект изменённым;
- снимается ли объект с поддержки;
- должно ли изменение выполняться в расширении.

Нельзя автоматически менять объект только потому, что файл доступен на запись.

---

# 69. Базовый принцип исследования

При неизвестной структуре:

```text
MODEL FIRST
PROJECT EXAMPLE SECOND
RAW XML LAST
```

То есть:

1. понять объектную модель;
2. найти аналог в текущем проекте;
3. только потом анализировать физическую сериализацию.
