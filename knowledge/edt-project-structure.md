# Структура проекта 1C:EDT

Уверенность: HIGH, если не отмечено иначе. Источник — проект-источник с
42 своими объектами (справочники, регистры, обработки, отчёты, роль,
подсистемы) и правками типовой конфигурации; все они обновляют базу из EDT.

## 1. Что где лежит

```text
<проект>/
├── .project, .settings/, DT-INF/PROJECT.PMF   — служебное, руками не трогать
└── src/
    ├── Configuration/Configuration.mdo         — корень: состав конфигурации, назначения, языки
    ├── Configuration/CommandInterface.cmi      — порядок разделов
    ├── Catalogs/<Имя>/<Имя>.mdo                — справочник
    │       Forms/<Форма>/Form.form + Module.bsl
    │       ObjectModule.bsl, ManagerModule.bsl (если есть)
    │       Templates/<Макет>/Template.dcs|.mxlx|.txt|.bin
    │       Commands/<Команда>/CommandModule.bsl (сама команда описана в <Имя>.mdo)
    │       Help/ru.html
    ├── Documents/<Имя>/…                       — так же, плюс проведение в .mdo
    ├── Enums/<Имя>/<Имя>.mdo
    ├── Constants/<Имя>/<Имя>.mdo
    ├── InformationRegisters/<Имя>/<Имя>.mdo + Forms/
    ├── AccumulationRegisters/<Имя>/<Имя>.mdo
    ├── CommonModules/<Имя>/<Имя>.mdo + Module.bsl
    ├── DataProcessors/<Имя>/<Имя>.mdo + Forms/ + Templates/
    ├── Reports/<Имя>/<Имя>.mdo + Templates/ОсновнаяСхемаКомпоновкиДанных/Template.dcs
    ├── Subsystems/<Имя>/<Имя>.mdo + CommandInterface.cmi + Subsystems/<Дочерняя>/…
    ├── Roles/<Имя>/<Имя>.mdo + Rights.rights
    └── CommonPictures/<Имя>/<Имя>.mdo + Picture.zip
```

Тип объекта задаёт папка первого уровня, объект — папка второго, описание —
`<Имя>.mdo` внутри. Формы, макеты и команды — папки внутри объекта, но их
ОБЪЯВЛЕНИЕ лежит в `.mdo` владельца (`<forms>`, `<templates>`, `<commands>`):
папка без объявления для EDT не существует, объявление без папки — ошибка
модели. См. `examples/metadata/*/`.

## 2. Файлы

| Правило | Почему | Пример / case |
|---|---|---|
| `.mdo`, `.form`, `.dcs`, `.cmi`, `.rights` — UTF-8 **без BOM**, переводы строк **CRLF**, отступ два пробела (в `.dcs` и `.rights` — табы) | Так пишет EDT; типовая конфигурация вся такая. Файл в LF EDT примет, но git покажет «изменён весь файл», а текстовый макет в LF платформа читает одной строкой | case 023 |
| `.bsl` — CRLF; BOM не ставить, но не считать ошибкой | EDT после ручной правки модуля в редакторе может сохранить его с BOM (ловили на модуле формы заказа) | case 026 |
| XML пишется в порядке, в котором его сохраняет EDT: значения по умолчанию не пишутся, порядок тегов задан моделью | Иначе после первого сохранения в EDT diff расходится на каждом элементе и правки пользователя не отличить от «переписал EDT» | case 027, `knowledge/managed-forms.md` |
| Новый файл создавать **копией рабочего аналога**, а не по памяти | Валидный XML ≠ правильный: форма без `saveWindowSettings` валидна и не рисуется | cases 001–004, `reference/INDEX.md` |
| Файлы, которые редактор EDT держит открытыми, снаружи не переписывать | Ломается модель рабочего пространства: «NullPointerException … formItem is null» при обновлении базы; лечится только «Проект → Очистить» | case 028 |

## 3. Полные имена (FQN)

Ссылки между объектами — всегда полное имя с классом: `Catalog.Имя`,
`Document.Имя`, `InformationRegister.Имя`, `CommonModule.Имя`, `Subsystem.Имя`,
`CommonPicture.Имя`. Форма — `Catalog.Имя.Form.ФормаЭлемента`, макет —
`Report.Имя.Template.ОсновнаяСхемаКомпоновкиДанных`, дочерняя подсистема —
`Subsystem.Родитель.Subsystem.Дочерняя`, стандартный реквизит —
`Catalog.Имя.StandardAttribute.Description`, команда навигации —
`Catalog.Имя.StandardCommand.OpenList`. Типы значений —
`CatalogRef.Имя`, `DocumentRef.Имя`, `EnumRef.Имя`, `CatalogObject.Имя`,
`DataProcessorObject.Имя`, `InformationRegisterRecordManager.Имя`, `DynamicList`,
`ValueTable`. Подробно — `knowledge/uuid-and-references.md`.

## 4. Configuration.mdo

Каждый объект верхнего уровня прописан строкой в своей группе:

```xml
  <catalogs>Catalog.ПримерСправочник</catalogs>
  <dataProcessors>DataProcessor.ПримерОбработка</dataProcessors>
```

Без строки объект лежит на диске, а конфигурация его не видит (case 021).
Строка встаёт последней в своей группе (`tools/edt_lib.register_in_configuration`).
Дочерние подсистемы в корень не прописываются — они у родителя в `<subsystems>`.
Общие картинки платформа держит по алфавиту (`подсистема_логистики.py`
вставляет на место). Там же у корня `<usePurposes>` — без `MobileDevice`
ни одна мобильная форма не откроется (case 005).

## 5. Свои объекты в типовой конфигурации

- Префикс имени (в проекте-источнике `мвм`): по нему проверки отделяют своё
  от типового, а `tools/check_project.py --prefix` проверяет только своё.
- Типовые объекты не пересоздавать: их `uuid` и состав — чужие. В них
  добавляются реквизиты (тоже с префиксом) и правятся формы идемпотентными
  вставками — `knowledge/generators.md`.
- Всё новое заводится сразу в подсистему (иначе объект недостижим кроме
  «Все функции») и, если есть свой справочный текст, — в справку тем же
  коммитом.

## 6. Что EDT делает с файлами

EDT читает файлы в модель (Big Model), проверяет, а базу обновляет из
модели, не из файлов. Отсюда:

- правку файла снаружи EDT подхватывает после «Обновить» (F5) проекта;
- если файл переписан, пока его редактор открыт, модель может остаться
  сломанной при целых файлах (case 028): проверить файлы без EDT —
  `1cedtcli export` в чистое рабочее пространство (`knowledge/validation.md`);
- модуль BSL в модель попадает текстом — его править можно свободно; `.mdo`
  и `.form` — сериализация модели, их порядок и состав тегов важны.

`DT-INF/PROJECT.PMF` хранит версию рантайма (у проекта-источника 8.3.27) и
версию хранилища; файлы EDT другой версии могут отличаться составом тегов
(MEDIUM — из `reference/edt-format-guide.md`, не проверялось).

## 7. Не путать с выгрузкой Конфигуратора

`Configuration.xml`, `Catalogs/Имя.xml`, `ConfigDumpInfo.xml` — другой формат
(выгрузка в файлы из Конфигуратора). Структура, имена тегов и состав свойств
там иные: `Attribute/Properties/Use`, `StringQualifiers/Length`. Знания из
`cases/024`, `cases/025` получены на нём и переведены на EDT с пометкой.
`1cedtcli export` умеет только ПОЛНУЮ выгрузку проекта в этот формат
(`knowledge/deployment.md`).
