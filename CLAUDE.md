# 1c-edt-skill — как работать с этим набором

Ты программируешь конфигурацию 1С:Предприятие в проекте **1C:EDT** (файлы
`.mdo`, `Form.form`, `Module.bsl`, `Template.dcs`, `.cmi`, `.rights`). Этот
набор — знания, рабочие примеры и кейсы, снятые с реальных проектов: типовая
ТЛЭиУА 1.1.36 / МВМ на платформе 8.3.24 (около 400 коммитов) и ФРЕГАТ EAM на 8.5.1
(EDT 2026.1) — 88 разобранных ошибок. Набор общий для всех 1С-проектов и
пополняется из каждого (см. «Пополнение набора»). Он заменяет память модели там,
где память ошибается.

## Главный принцип

**WORKING EXAMPLE > ABSTRACT KNOWLEDGE > MODEL MEMORY.**

Порядок доверия: (1) файл, который работает в базе (`examples/`,
`reference/`), (2) правило в `knowledge/` со ссылкой на кейс, (3) то, что ты
«помнишь» о формате EDT. Если правило и пример расходятся — верен пример; если
память и правило расходятся — верно правило. Всё, что ты пишешь по памяти без
образца, помечай в отчёте как непроверенное.

Нет ни образца, ни правила — **документация платформы на ИТС** (its.1c.ru, напр. `db/v851doc` — Руководство
разработчика 8.5.1), а не память. Она открывается только после входа: открой страницу во встроенном браузере и
**попроси пользователя войти** (логин и пароль сам не вводишь, даже если их прислали в чат), затем читай текст
страницы. Имена свойств встроенного языка и их английские пары (теги XML) — строками UTF-16 в dll платформы
(`mngcore.dll`, `mngdsgn.dll`). Case 085.

## Алгоритм (10 шагов)

1. **Определи вид задачи**: новый объект / реквизит в существующем / форма /
   модуль / запрос / отчёт / подсистема-роль / правка типовой / мобильный
   экран / поле HTML / диагностика ошибки. Открой `index/patterns.md`
   («хочу сделать X») или `index/topics.md` (по теме). Диагностика — сначала
   `knowledge/common-errors.md` по тексту симптома.
2. **Найди рабочий пример и боевой образец**: README примера в `examples/…`
   (что можно менять, что нельзя) и строку в `reference/INDEX.md`. Копируй
   структуру целиком — не собирай XML из головы.
3. **Прочитай правила**: раздел `knowledge/*.md` по теме и кейсы, на которые
   он ссылается (`cases/NNN-*/lessons.md`, `before/` → `after/`). Заметь
   confidence: HIGH — делать так; MEDIUM — так работает, проверить в базе;
   LOW — только направление.
4. **Проверь целевую конфигурацию**: префикс имён, версия платформы,
   иерархичность справочников, которые читаешь (`<hierarchical>` в .mdo),
   существующие имена (ключевые слова запросов запрещены), длины строк
   ≤ 1024, типовые объекты, на которые опираешься (сверять по .mdo, не по памяти).
5. **Сделай изменение** через `tools/scaffold.py` (копия примера с
   переименованием и uuid5) или `tools/edt_lib.py` / скрипт по образцу
   `reference/generators/`. Генератор проекта = спецификация + вызовы
   `edt_lib`; форматы заново не изучать и не переписывать — чего в `edt_lib`
   нет, добавить в него. Новый объект = четыре места сразу: файлы объекта,
   строка в `Configuration.mdo`, подсистема (`content` + `.cmi`), роль.
   uuid — устойчивые (uuid5), не случайные. Ручная правка XML — только
   фрагментом, снятым с образца, в порядке тегов EDT, без умолчаний.
6. **Прогони проверки до нуля ошибок**: `python tools/check_project.py <корень
   EDT> --prefix <префикс>`, `python tools/check_bsl.py <модуль> [--hier …]`.
   Каждое сообщение проверки ссылается на кейс — прочитай его, не глуши проверку.
7. **Сверь с образцом** глазами: скелет элемента формы (порядок дочерних
   тегов), спутники таблиц, четыре свойства групп, `saveWindowSettings`,
   `numberQualifiers`, три пространства номеров, место ссылок на формы в .mdo,
   `parentSubsystem` у дочерних подсистем. `git diff` — только ожидаемые строки.
8. **EDT**: закрыть редакторы форм перед перезаписью файлов снаружи; обновить
   проект; Problems чисто; открыть форму (пустой лист → лесенка проб, case 006).
   Обновление базы — только из EDT; новые объекты — полное обновление.
9. **Прогон в платформе** — сначала автоматически (`knowledge/testing.md`):
   `tools/platform.py … load` (или `quick`), `update`, `com reports`, `screens`, `forms`, `ui` (настоящие нажатия по сценарию);
   затем руками: открыть каждую форму, нажать каждую команду,
   выполнить сценарий с данными (включая группы иерархических справочников,
   пустые ТЧ, чистую базу). Запросы, директивы, имена свойств проверяются
   только здесь. Сообщение платформы читать целиком — оно называет виновника.
10. **Отчёт**: что сделано (файлы), какой уровень проверки пройден
    (`knowledge/validation.md` §5), что не проверено и почему. Новая ошибка →
    новый кейс в `cases/` (папка `NNN-slug`) по шаблону (task / before / after / lessons)
    и строка в `knowledge/common-errors.md`.
    После каждой большой работы в отчёте — **чистое время Claude** на неё:
    `python <skill>/tools/claude_time.py --с "фрагмент запроса"` из каталога проекта (по транскрипту сессии;
    ожидание пользователя и фоновых прогонов не считается). В документах для заказчика — по просьбе пользователя.

## Чего не делать никогда

- Не писать `Form.form`/`.mdo` с нуля по памяти; не копировать XML из выгрузки
  Конфигуратора (другой формат — `reference/edt-format-guide.md` §2).
- Не убирать «лишние» теги из образца (спутники, свойства групп,
  `saveWindowSettings`) — они не лишние (cases 001–004, 007).
- Не нумеровать колонки таблицы заново с единицы (case 003).
- Не менять uuid существующего объекта и не пересобирать объекты со
  случайными uuid (case 020).
- Не писать процедуру модуля формы без директивы (case 011); не занимать
  имена `Параметры`, `Объект`, `Элементы`, `ЭтаФорма` (case 010).
- Не называть реквизиты ключевыми словами запросов (case 016); не заводить
  строки длиннее 1024 (case 024).
- Не читать регистр через `Получить` для проверки наличия записи (case 018).
- Не скрывать элементы типовой формы правкой XML — модуль под константой (case 037).
- Не грузить базу мимо EDT (`knowledge/deployment.md` §1).
- Не переносить в конфигурацию адреса, учётные записи и реальные данные.
- Не утверждать «работает», если прогон в базе не сделан.

## Пополнение набора (из любого проекта)

Набор один на машине: репозиторий `C:\1c-edt-skill` (git `JukuMonk/1c-edt-skill`);
`~/.claude/skills/1c-edt-skill` и папки `1c-edt-skill` в проектах — ССЫЛКИ
(junction) на него. Поэтому:

- **Никогда не копировать** набор в `~/.claude/skills` или в проект (`cp -r`,
  `robocopy`, `shutil.copytree`) и не удалять эти папки — через ссылку это
  пишет в общий репозиторий или стирает его. Правки — прямо в `C:\1c-edt-skill`.
- Перед правкой: `git -C C:\1c-edt-skill fetch` и `git status` — параллельно набор пополняют
  другие проекты (здесь и на других машинах); порядок слияния — «Параллельные правки» ниже.
- Новый урок (ошибка, которую пришлось разбирать; формат, которого нет в
  `examples/`) → кейс `cases/NNN-slug/` (`task.md` с **проектом и платформой**,
  `before/`, `after/`, `lessons.md`) + строка в `index/cases.md` и
  `knowledge/common-errors.md` + счётчик кейсов в README/CLAUDE/SKILL — в ОДНОМ
  маленьком коммите. Номер — следующий свободный на момент коммита.
- Доработка `tools/edt_lib.py` — только совместимая: новые функции и
  параметры по умолчанию; поведение существующих не меняется без явной причины.
- Общее — в наборе; генераторы и данные конкретного проекта — в репозитории
  проекта (в наборе — только образец в `reference/` с пометкой проекта).
- Отправка в GitHub (`git push`) — только с согласия пользователя.

## Параллельные правки из разных проектов (слияние на GitHub)

Типичная коллизия: проекты A и B взяли версию N, каждый дописал своё (N+A, N+B); A отправил первым, у B `git push`
отклонён или при слиянии конфликт. Порядок для того, кто сливает вторым (агент делает сам, кроме `push`):

1. **Начало работы**: `git fetch`; если `main` позади `origin/main` — `git pull --rebase` (до своих правок это без
   конфликтов). Правки — маленькими коммитами: один урок = один коммит, в сообщении — проект («(ZHDRM, …)»);
   кейс и доработку `tools/` не смешивать.
2. **Номер нового кейса** — `python tools/cases_sync.py следующий` (максимум из своих папок, `origin/main` и
   указателя + 1). Гонку это не исключает: номер окончательно закрепляется при слиянии (п. 4).
3. **Слияние**: `git fetch` → `git rebase origin/main` (не merge: история линейная, каждый урок — свой коммит;
   конфликт решается по коммиту) → правила п. 4 → `python tools/cases_sync.py проверить` и
   `python tools/check_links.py` без ошибок → `git push` (с согласия пользователя). Отклонён (кто-то успел) —
   повторить с `git fetch`. С pull request — то же в ветке `проект/тема`.
4. **Правила конфликтов**:
   - **номер кейса занят** (в `origin/main` своя папка `cases/NNN-…`): отправленный кейс номер сохраняет, свой —
     `python tools/cases_sync.py перенумеровать NNN MMM` (без `--применить` — просмотр каждой замены), MMM —
     `следующий`; затем `--применить`;
   - **добавочные файлы** (`index/cases.md`, `knowledge/common-errors.md`, разделы `knowledge/*.md`, `lessons.md`):
     сохранить ОБЕ стороны, свои строки — после чужих, по номеру кейса. `index/cases.md` и `common-errors.md` git
     сливает объединением сам (`merge=union` в `.gitattributes`) — проверить дубли и порядок;
   - **счётчики кейсов** (README, CLAUDE, SKILL, заголовок указателя) не прибавлять руками —
     `python tools/cases_sync.py счётчики` пересчитывает по папкам;
   - **`tools/*.py`**: правки разных функций сохраняются обе; одна функция у обоих — объединить вручную, сохранив
     совместимость (новые параметры — со значением по умолчанию), и прогнать проверки инструмента
     (`make_examples.py`, `check_project.py`; для `designer_lib` — сверку в проекте, который его правил);
   - **противоречащие правила `knowledge/`** не выбирать молча: оставить оба с проектом и платформой (правило
     может зависеть от 8.3.24 / 8.3.27 / 8.5) и сказать пользователю.
5. **После слияния** — строка в отчёте пользователю: какие номера перенумерованы и какие правила объединены.

## Формат файлов

UTF-8 **без BOM**, **CRLF**, отступы 2 пробела в `.mdo`/`.form`/`.cmi`,
табуляция в `.bsl`/`.dcs`/`.rights`. Файлы читать и писать с `newline=''`.

## Карта набора

- `knowledge/testing.md` — проверка в платформе, 9 уровней (загрузка, обновление ИБ, COM, снимки и все формы, заполненность, сценарии, поле HTML, настоящие нажатия); `tools/platform.py`, `tools/register_com.py`.
- `knowledge/new-project.md` — старт нового проекта из `.dt`; `tools/new_project.py` + `bootstrap/`.
- `knowledge/designer-format.md` — работа БЕЗ EDT: выгрузка Конфигуратора, внешние обработки, сборка и загрузка пакетным Конфигуратором, проверка через COM и TestManager; `tools/designer_lib.py`.
- `knowledge/` — 17 тем (`edt-project-structure`, `metadata`, `managed-forms`,
  `mobile-forms`, `bsl`, `skd`, `subsystems-and-ui`, `roles`,
  `html-field-and-templates`, `uuid-and-references`, `deployment`,
  `generators`, `validation`, `common-errors`, `testing`, `new-project`,
  `designer-format`).
- `examples/` — 12 видов метаданных, 4 формы, мобильная форма, 2 отчёта,
  8 фрагментов BSL; README у каждого; собираются `tools/make_examples.py`.
- `cases/` — 88 кейсов; указатель `index/cases.md`.
- `reference/` — боевые файлы и генераторы; указатель `reference/INDEX.md`.
- `tools/` — `edt_lib.py` (сборка XML), `check_project.py`, `check_bsl.py`,
  `scaffold.py`, `make_examples.py`, `make_sandbox.py`, `check_links.py`, `platform.py`, `vanessa.py`,
  `claude_time.py` (чистое время Claude по транскрипту — для отчёта).
- `tests/tasks.md` — 24 задачи с критериями; решения в `tests/expected/`;
  песочница `tests/sandbox/`.
