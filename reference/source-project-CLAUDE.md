## Что это за проект

Диспетчерский интерфейс внутризаводской логистики АО «Метровагонмаш» (ТМХ). Карта
(Leaflet) для управления заявками и рейсами перевозок между складами/цехами. Встраивается
в поле HTML внешней обработки **1С УАТ** (тонкий клиент, движок V8WebKit). Умеет работать
автономно (демо-режим). Статус — рабочий прототип первого приближения.

## Главный файл

Идёт модуляризация (`ПЛАН-МОДУЛЯРИЗАЦИИ.md`). С шага 1 источник правок —
**`src/index.html`** (оболочка) плюс вынесенные фрагменты в `src/*`. Сборка `build.py`
склеивает их в `dist/`.

**`02-прототип-исходники/genplan-dispatch-prototype.html` — ЗАМОРОЖЕН.** Это эталон, с
которым сборка сверяется побайтово; править его нельзя, иначе теряется критерий «1:1».
То же для `02-прототип-исходники/genplan-1c.html`.

**Пользователь правит формы прямо в EDT — и это надо переносить в генератор.**
Порядок: HEAD проекта EDT → генераторы → сравнить с текущим файлом
(`выделить_правки.py`); всё, что в разнице, — либо правка пользователя, либо
то, как EDT переписал наш XML при сохранении. Цель — «строк разницы 0»:
тогда пересборка ничего не потеряет. Идемпотентные шаги типовых форм чужие
правки не трогают, генераторы наших объектов перезаписывают файл целиком.

Модуляризация закончена, правила выноса — в шапке `build.py` и в разделе 8
`ПЛАН-МОДУЛЯРИЗАЦИИ.md`. Побайтовая сверка с эталоном была её критерием и теперь идёт
только по флагу `--сверка`: с содержательными правками расхождение — норма. Чтобы
доказать, что правка косметическая, есть `инструменты/сверить_код.py` — он сравнивает
потоки токенов, поэтому комментарии и форматирование расхождением не считает, а
изменение кода считает.

- **Метки вставки ставить с нулевой позиции.** Метка заменяется по месту, и её отступ
  достаётся первой строке фрагмента (ловили: `    var $d` вместо `  var $d`).
- **Границу выноса задавать содержимым** (`--первая`), а не только счётом строк. Байтовая
  сверка съезд границы НЕ ловит: склейка сходится, а файл начинается осиротевшей скобкой
  от предыдущей функции (ловили на всех десяти файлах карты сразу).

Проверка правок (обязательна перед завершением):
1. `python build.py` — должен пройти сверку 1:1 и напечатать «Совместимо.».
2. Прогон в браузере (см. ниже) — демо сеется, назначение работает, движение идёт,
   сводка рисуется, 0 ошибок в консоли.
3. **`python инструменты/арм_диспетчера.py` — уложить макет карты в проект EDT.**
   `build.py` собирает только `dist/`; без укладки база показывает СТАРУЮ карту
   (ловили: «не маршрута, не геозоны, не сворачивания — ничего не вижу»).
4. Коммит после каждого рабочего шага.

- **playwright не установлен**, `file://` в браузере агента запрещён. Прогон так:
  `python -m http.server 8777 --directory dist` (описан в `.claude/launch.json`) и
  открыть `http://localhost:8777/genplan-dispatch-prototype.html`.
- В скрытой вкладке браузера **не работает requestAnimationFrame** — машины стоят.
  Это не поломка: чтобы проверить движение, вызвать `шагДвижения()` вручную между
  замерами `marker.getLatLng()`. Само движение с 25.08.2026 идёт на `setInterval`
  (см. ловушку про rAF в поле 1С), так что достаточно подождать.
- Выезд рейса — ручное действие диспетчера (кнопка `#dcGo`), в `window.Диспетчер` его нет.
- **Файлы читать и писать только с `newline=''`** (и `encoding='utf-8'`). Иначе Python на
  Windows подменит `\n` на `\r\n` при записи и весь файл разойдётся с эталоном.
- В git выключен `core.autocrlf` — файлы для 1С должны лежать побайтово как есть.
- Heredoc (`cat > файл <<'EOF'`) в Git Bash рвётся на больших файлах — писать файлы
  инструментом Write или скриптом.

## Новое всегда попадает в два места

Любой новый объект конфигурации (справочник, регистр, обработка, отчёт,
общий модуль) кладётся **в подсистему И в справку** тем же заходом, что и
сам объект:

- **в подсистему** — иначе в интерфейсе его нет вовсе: до него не добраться
  иначе как через «Все функции». Состав держит `подсистема_логистики.py`
  (`ВЕРХНИЙ` и `ГРУППЫ`); он же теперь ПАДАЕТ, если в проекте есть объект
  `мвм*`, не внесённый в состав;
- **в справку** — раздел в `src/dispatch/37-справка.js`. Справка лежит в
  коде именно затем, чтобы правиться тем же коммитом, что и поведение:
  справка, которую надо править отдельно, устаревает первой.

## Жёсткие правила (нарушение ломает бой)

- **Только ES2018.** Нельзя `?.`, `??`, top-level await, приватные поля классов. Среда —
  V8WebKit в поле 1С. Проверка — `node --check` / `es_check.js`.
- **Никаких тяжёлых внешних библиотек** графиков/UI. Вся инфографика рисуется вручную на
  SVG.
- **Идентификаторы в коде — кириллица** (сознательный выбор). ОСТОРОЖНО с латинскими
  двойниками (`вод`/`вoд`, `Диспетчер`/`Диспeтчер`) — ломают текстовые замены. При правках
  всегда перепроверяй идентификаторы; для правок кириллично-насыщенного кода предпочитай
  скрипты (Python), а не ручной поиск-замену.
- **Файлы для 1С — UTF-8 с BOM** (`EF BB BF`). Без BOM 1С читает как Windows-1251 →
  кракозябры. Касается Module.bsl, макета КартаHTML, всех XML.
- **localStorage в поле 1С ненадёжен.** Используем в try/catch; для боевого постоянства —
  писать в справочник/константу 1С.

## Ловушки, на которых уже спотыкались (не повторять)

- **Имена значений перечислений сверять с `.mdo`, а не сочинять.** Написал
  `Перечисления.мвмРежимДоступаГеозоны.Запрет`, а значение называется
  `ЗапретитьВыбранным` — 1С сказала об этом только в бою, «Поле объекта не
  обнаружено (Запрет)». Сверяет `python инструменты/проверить_перечисления.py`
  (все наши модули против выгрузки EDT).

- **Выбрасывая запрос из пакета, считай разделители.** Убрал запрос вместе
  с «;» ПЕРЕД ним — остался «;» ПОСЛЕ, и два подряд означают пустой запрос:
  «Ожидается выражение "ВЫБРАТЬ"». Роняет весь пакет, то есть всё
  назначение рейсов разом. Ловит `запросы_1с.py`.

- **Читать `Результаты[N]` по голому числу нельзя.** Позиция — единственная
  связь запроса с его результатом, и вставка запроса в СЕРЕДИНУ пакета молча
  сдвигает всё, что ниже. Три запроса геозоны (весогабариты, установленная и
  закреплённая техника) встали после контура, типы ТС уехали с позиции 2 на 5 —
  и «ТС» стало читаться из запроса типов: «Поле объекта не обнаружено (ТС)»
  при перечитывании из 1С. Вылезло не сразу: пустая табличная часть к полю не
  обращается вовсе, так что ошибка ждала первой геозоны с техникой. Индексы
  держать поимённо (`ТипыТСЗапрос = 5`), а сверяет их `запросы_1с.py` —
  поле из `Результаты[N]` обязано существовать в N-м запросе пакета.

- **Необязательный расчёт в сборке пакета — только внутри `Попытка`.** Та же
  опечатка уронила ЗаполнитьПутиРейсов, а вместе с ней всю сборку пакета:
  АРМ открылся пустым, без узлов, заявок и парка. Украшение (пути для
  анимации) не имеет права ронять данные.

- **Запрос к ИЕРАРХИЧЕСКОМУ справочнику обязан отсекать группы.** Реквизиты
  по умолчанию заводятся «для элемента», и у ГРУППЫ реквизиты возвращают
  NULL: `Окр(Выборка.Грузоподъемность * 1000)` падает «Преобразование
  значения к типу Число не может быть выполнено» — и роняет сборку ВСЕГО
  пакета, АРМ не открывается. В базе разработчика этого можно не увидеть
  годами: демо заводит плоские элементы. Вылезло на чистой базе, где группы
  типов ТС создало типовое первоначальное заполнение. Из наших запросов
  групп не отсеивали шесть. Ловит `запросы_1с.py` (сверяет с `hierarchical`
  в выгрузке EDT), лечит `инструменты/группы_не_элементы.py`.

  Обратная сторона той же привычки: у ПЛОСКОГО справочника поля
  `ЭтоГруппа` нет вовсе — «Поле не обнаружено», и запрос падает так же
  в бою. Иерархические из наших — только `уатГеозоны_уэ` и
  `уатПунктыНазначения`; узлы, проезды и все типы плоские. Ловит тот же
  `запросы_1с.py` — он же теперь читает запросы из схем компоновки
  (`.dcs`) наших отчётов: там текст запроса лежит в XML, и ни один
  компилятор его до боя не увидит.

- **НОВЫЕ объекты метаданных база принимает только при ПОЛНОМ обновлении.**
  «Ошибка добавления объекта DataProcessor uuid=… : нельзя добавлять объекты
  метаданных без загрузки родительского объекта» — это не про формы и не про
  uuid: инкрементальная загрузка умеет менять существующие объекты, но не
  добавлять новые. Когда в проекте появились обработки, отчёты, роль или
  общий модуль, первое обновление конфигурации ИБ должно быть полным; дальше
  снова хватит инкрементального. Отсюда же правило: uuid объектов держать
  УСТОЙЧИВЫМИ — пересборка со случайным uuid делает объект новым, и база
  снова требует полной загрузки.

- **Дочерняя подсистема в EDT — это тег `<parentSubsystem>`, а не вложенная
  папка.** Папка только место хранения; связь «кто чей» держит строка в .mdo
  дочерней: `<parentSubsystem>Subsystem.Родитель</parentSubsystem>` (у
  двухуровневых — `Subsystem.А.Subsystem.Б`). Без неё EDT дочерней подсистему
  не считает: в родителе ссылки есть, а объекта в модели нет. Инкрементальная
  загрузка отвечала «нельзя добавлять объекты метаданных без загрузки
  родительского объекта», полный импорт — «Файл объекта не существует …
  /Subsystems/мвмПланЗавода.xml». Три захода (без групп → с группами →
  переименование) ушли на поиск причины не там: дело было не в порядке
  загрузки. Ловит `подсистема_логистики.py` — он проверяет ссылку у каждой
  дочерней.

- **Подача от места машины — украшение, а не условие рейса.** Маршрутный лист
  начинается там, где машина стоит, а стоит она в ГАРАЖЕ — это пункт назначения
  из справочника ТС, и к узлу карты его никто не привязывал: узлы рисует
  диспетчер. Отрезок подачи не строился, и назначение отказывало ЦЕЛИКОМ по всем
  четырнадцати заявкам разом — «Маршрут для этой машины не построен», хотя сам
  рейс «цех → цех» считался. Точка подачи теперь добавляется, только если путь
  до погрузки действительно есть. Та же ошибка, что с ЗаполнитьПутиРейсов выше.

  Проверка привязки в демо при этом бодро печатала «все 3 пункта маршрутов
  связаны с узлами карты»: она смотрела только пункты маршрутов и молчала о
  гараже. **Проверять надо все пункты, участвующие в рейсе**, а не те, что на
  виду. И называть виноватого по имени: «Пункт назначения не привязан» звучит
  одинаково для погрузки, разгрузки и места машины.

- **«Лишнее» — это то, чего нет в ПАКЕТЕ, а не то, что не записалось.** Запись
  графа пропускала геозону с контуром короче трёх точек (`Продолжить`), а
  следом пометка лишних снимала всё, чего нет в списке ЗАПИСАННЫХ, — и зона,
  которую диспетчер только что нарисовал, исчезала после перечитывания. Молча:
  транзакция фиксировалась, ошибки не было. Каждый `Продолжить` в записи обязан
  класть объект в список оставшихся (`ОставитьПропущенную`) и называть причину.

- **Настройка из регистра переживает свой интерфейс.** Подписи узлов стали
  белыми на белом чертеже: раздел «подписиУзлов» в регистре настроек карты
  хранил цвет с тех времён, когда подписи красили на вкладке «Настройки», и
  перекрывал умолчание. Палитру оттуда давно убрали — поправить цвет стало
  негде, а запись осталась. Убирая интерфейс правки, убирайте и чтение
  настройки: оформление теперь задаёт ТИП узла.

- **«СтоянкаПунктОтправления» в заказе — это ЧИСЛО, а не пункт.** Пункты
  маршрута живут в ТЧ `ПромежуточныеПункты` (поле `Пункт`, тип составной:
  ссылка ИЛИ строка-адрес), и их может быть больше двух. «ТребованиеКТС» —
  ссылка на МОДЕЛЬ ТС, а не на машину: маршрутизации она не годится. Имя
  реквизита обещает одно, тип говорит другое — сверять по CSV, а не по имени.
  Там же: `Паллета` в строке маршрутного листа — СТРОКА, и вида упаковки
  через неё не достать; норматив берётся из грузового состава заказа.

- **Единицы у типовых реквизитов читать в СИНОНИМЕ, а не угадывать.** В УАТ
  габариты (`ГабаритныйРазмерШирина`, `ПолезныйРазмерДлина`) — в **мм**, а
  `Грузоподъемность` — в **тоннах**; так и написано: «Полезная длина (мм)»,

- **Даты в шапке маршрутного листа считает типовой, и не всегда по факту.**

- **Имя реквизита не должно быть ключевым словом ЗАПРОСА.** Назвал ресурсы

- **Пока идёт длинный серверный вызов, поле HTML продолжает принимать клики.**

  щелчок кладёт команду в очередь и заставляет движок работать поверх занятого
  клиента. Вызовы обработчика ожидания за это время копятся и выполняются
  подряд, когда клиент освободится. Пользователя на таком щелчке по карте
  ВЫБРОСИЛО из 1С целиком. Лечится с обеих сторон: карта на время записи
  закрывается шторкой (глотает мышь и клавиши, останавливает движение), а
  модуль отключает `ОпросМоста` до конца записи и включает его в `Попытка` —
  онемевшая карта хуже ошибки.

- **Убрал элемент из разметки — проверь, кто в него пишет.** Часы диспетчера
  раз в секунду писали в удалённый `#kpiClock`, мост исправно слал каждое
  исключение в 1С, и очередь команд забилась до 99 записей за минуту. Обращения
  к необязательным элементам оборачивать проверкой.
- **Вывод скрипта в конвейер — всегда UTF-8.** `build.py` печатал в кодировке
  консоли, и `инструменты/проверка_защит.py` читал кракозябры: все четыре пробы
  разом «переставали ловить», хотя защиты работали.

- **Писать текст в панель из таймера — только при изменении значения.** Маркеры
  Leaflet двигаются через transform и макет не трогают, а запись `textContent`
  в разметку панели — перекладка макета всей страницы в V8WebKit. Процент доли
  пути, писавшийся каждые 400 мс, вешал обработку с момента открытия карточки
  рейса (до неё элемента нет — и не тормозит). Сравнивать с текущим содержимым
  (чтение `textContent` перекладки не вызывает) и держать ширину элемента
  фиксированной, чтобы смена «9%»→«10%» не двигала соседей.
- **Бесконечные CSS-анимации и `backdrop-filter` в поле 1С — цена, а не
  украшение.** Поле HTML рисует без аппаратного ускорения: пульсация кольца на
  каждом маркере техники (`animation … infinite`), бегущая штриховка маршрута
  (`stroke-dashoffset`) и размытие фона у плашки-подсказки повесили обработку
  наглухо, как только машин на плане стало сорок пять вместо двух. Сам JS был
  ни при чём — шаг движения 0.3 мс на 13 машин. Держать такие эффекты штучно
  (у выбранного объекта) или не держать вовсе.
- **Место машины на плане — не только гараж.** Маркер техники создавался лишь
  тогда, когда `Гараж` ТС привязан к узлу графа, а в УАТ он заполнен не у всех.
  Машина с назначенным рейсом и посчитанным путём оставалась без маркера и,
  разумеется, никуда не ехала: вести было нечего. Источники места по порядку —
  узел текущего рейса, точка погрузки/разгрузки её листов, и только потом
  гараж; без всего этого машину на карте по-прежнему не рисуем.
- **Каждый canvas-рендерер Leaflet глушит клики нижних канвасов.** DOM-событие
  достаётся верхнему канвасу, хит-тест ищет только среди ЕГО фигур, при
  промахе вниз ничего не проваливается. Пустой канвас узлов лишил кликов
  линии в редакторе, канвас рёбер — геозоны (их карточка кликом не
  открывалась никогда). Право перехвата — только у канваса, чьи фигуры
  сейчас интерактивны; остальным `pointer-events:none`
  (`обновитьПерехватКанвасов` в 16-modes, зовётся из setMode и смены
  инструмента).
- **`requestAnimationFrame` в поле HTML 1С не гарантирован.** Окно тонкого клиента
  для планировщика анимации может быть «невидимым», и кадры не приходят вовсе:
  машины стояли при верных данных, а в браузере всё ехало — воспроизвести не на
  чем. Периодическую работу вести `setInterval` (на нём держится и мост, опрос
  раз в 40 мс), rAF оставлять только для разовых пересчётов вёрстки.

  На том же rAF висит и **перерисовка canvas у Leaflet**: `_requestRedraw`
  откладывает её кадром, а на canvas у нас круги узлов, дороги и геозоны. Кадр
  не приходил — canvas оставался пустым, и граф ПРОПАДАЛ с плана после каждого
  `renderGraph`, то есть при любом переключении вкладок; возвращался только от
  движения карты (на `moveend` Leaflet рисует синхронно). Лечится таймерной
  заменой `requestAnimationFrame` в `src/index.html` **до** библиотеки: Leaflet
  запоминает функцию в момент разбора файла, поздняя подмена бесполезна.
  Порядок стережёт сборка (`проверить_замену_raf`), проба — в проверке защит.
  Воспроизводится в браузере: убить rAF скриптом в `<head>` копии сборки.

  **Граф рисуется SVG, а не canvas** (`ГРАФ_SVG` в `11-render.js`). Канвасы в
  поле 1С теряют содержимое: пропадает то одно, то другое — в диспетчере
  исчезают кружки узлов, дороги остаются, — не с первого зума, а с третьего-
  четвёртого, и возвращается после переключения вкладок. Общее у пропадающего
  одно: это canvas; DOM-подписи и divIcon-маркеры редактора не пропадали ни
  разу. Канвасов было три (геозоны, дороги, узлы), каждый зум пересоздаёт
  буфер каждого. SVG буферов не требует. Переключатель «Рисовать граф как SVG»
  на вкладке «Настройки» возвращает canvas — он быстрее на сотнях объектов.

  Замены rAF ДОСТАТОЧНО — и ничего сверх неё делать не надо. Попытка
  «помочь» прямыми вызовами приватных `_update()` и `_redraw()` рендерера
  стоила недели: с неё рёбра начали пропадать при зуме. `_update()`
  перезаписывает `_zoom` и `_center` рендерера, а это опорная точка, от
  которой Leaflet считает трансформ контейнера при следующем зуме; вызванный
  не в свой момент, он уводит канвас с экрана. **Не управлять перерисовкой
  Leaflet снаружи** — чинить надо то, на что он опирается (кадры), а не
  дёргать его внутренности. Что творится с канвасами, показывает кнопка
  «Проверить»: пейн, число фигур, размер, сдвиг и непрозрачные пиксели.
- **Не называй локальные переменные `N`, `E`, `FLEET`.** Локальная `var N` из-за hoisting
  перекрывает глобальный `N` (узлы карты) — весь посев демо молча ломается.
- **Прогресс движения** машин считать в шкале `Date.now()` (рейс.выезд в ней), а НЕ по
  таймстампу из requestAnimationFrame (это performance.now() — другая шкала, прогресс
  выйдет 0).
- **Подложку из CAD-PDF не делать SVG** — получается ~48 МБ. Только высокоразрешающий PNG
  в палитре 256.
- **Смена подложки: важны пропорции и кадр, а не разрешение.** Картинка растягивается на
  `bounds` (ширина плана = `worldW` = 1500 единиц, высота — из `IMG_H/IMG_W`), а узлы
  графа хранятся в этих единицах абсолютно. Значит 12000px и 8000px равнозначны, а вот
  другое соотношение сторон или другой кадр съезд гарантируют. Пропорции сверяет сборка
  (`проверить_подложку`), кадр — только глазами по опорным объектам.
- **Константы 1С в XML** грузятся с ошибками — создавать вручную в Конфигураторе.
- **`03-1С-интеграция/КартаHTML-макет.txt` — копия из `dist/`**, обновлена 21.08.2026
  (до этого там лежала сборка старой версии, отставшая на 77 участков). Эталоном для
  сверки не служит: собирается из `src/`, при правках копировать заново из `dist/`.
- **XML объектов конфигурации** — строго под версию метаданных ЦЕЛЕВОЙ конфигурации, по
  образцу реальной выгрузки, а не из шаблонных примеров.

## Архитектура (кратко)

Единый HTML = три области:
1. **Область карты** — Leaflet (CRS.Simple), подложка-генплан растянута под мировые
   границы `IMG_W=2600 × IMG_H=1839` (соотношение 1.413). Здесь: `N` (узлы), `E`
   (проезды), `FLEET` (45 машин), `dijkstra`/`routeGeom` (маршруты), `NODE_STYLE`/
   `GEO_TYPES`/`CFG` (стили), `анимироватьРейсы` (движение), `paintFleet` (парк).
2. **Диспетчер** (IIFE → `window.Диспетчер`) — `ЗАЯВКИ`/`РЕЙСЫ`, планировщик, рендер,
   `посеятьДемо`, публичный API (`заявки`, `рейсы`, `назначить`, `выбратьРейс`,
   `очередьМашины`, `обновить`).
3. **Редактор графа и геозон** — правка узлов/дорог/зон поверх генплана.

Планировщик: у каждой машины персональная очередь рейсов; прогноз по цепочке; глобальное
перепланирование по приоритету при новой заявке/отмене (закреплённые не трогаются);
ручное управление кнопками. Подробно — `КАК-ПРОДОЛЖИТЬ.md`, разделы 5–6.

## Боевая конфигурация УАТ

Выгрузка целевой конфигурации — **`ConfigUAT/`** (1С:ТЛЭиУА КОРП 1.1.36.1, 1С-Рарус):
именно в неё пойдут доработки и в неё встраивается обработка диспетчера. В git её нет
(760 МБ, 30 169 файлов, пересобирается из Конфигуратора) — вместо неё в репозитории
справочник метаданных, он же точка входа при переписывании запросов `Module.bsl`:

- `03-1С-интеграция/УАТ-объекты.md` — 1938 объектов по типам, имя + синоним;
- `03-1С-интеграция/УАТ-реквизиты.csv` — 15 216 реквизитов (объект, табличная часть,
  вид поля, имя, синоним, тип значения). Ищется grep'ом, открывается в Excel.

Пересобрать: `python инструменты/справочник_уат.py` (файлы перезаписываются целиком).

**Модуль формы АРМ (`03-1С-интеграция/Module.bsl`) собирается цепочкой скриптов
в строгом порядке** — она записана в `03-1С-интеграция/СБОРКА-МОДУЛЯ.md`. Новую
доработку модуля добавлять отдельным идемпотентным скриптом и дописывать в ту
таблицу, а не править модуль руками: прямая правка теряется при пересборке.

Доработки метаданных по ТЗ делает `инструменты/метаданные_уат.py` — он же источник
правды по ним (выгрузки в git нет). Перед загрузкой в 1С —
`python инструменты/проверить_метаданные.py`. Три правила, на которых уже спотыкались:

- **Файлы выгрузки — UTF-8 с BOM и CRLF.** Иначе Конфигуратор ругается или читает
  кракозябры.
- **Состав свойств брать из живого образца выгрузки, а не выдумывать.** У реквизита
  табличной части свойств меньше, чем у реквизита справочника (нет
  `FillFromFillingValue`, `FillValue`, `Use`) — 1С отвергает файл.
- **Валидный XML ≠ правильный XML.** `ET.parse` пропускает файл, где значение уехало
  в соседний тег; 1С — нет («Ошибка XDTO … при чтении свойства AllowedLength`»).

**Рабочая база с 04.09.2026 — «МВМ локальная»**, публикация
`http://<сервер>/<база>  (адрес вычищен из skill pack)`: в неё загружен .dt боевой базы (план
завода и граф там актуальные), конфигурация — из проекта EDT. Пользователи
в ней боевые: демо-посев на ней не запускать. `обновить_и_запустить.py`
ходит на этот адрес, если не находит автономного сервера (`--адрес`,
`--пользователь` переопределяют). Блок ниже про автономный сервер —
история: приложение «УАТ МВМ» удалено.

**Базу держал АВТОНОМНЫЙ СЕРВЕР EDT**, а не файловый доступ. `ibsrv.exe`
слушает порт из `config.yaml` (у нас 8319) и обслуживает каталог
`C:\Users\user\Documents\InfoBase9`. Пока сервер работает, открыть тот же
каталог файлом нельзя: клиент стартует, показывает «Загрузка конфигурационной
информации…» и молча исчезает — без единого сообщения. Подключаться надо так
же, как это делает EDT: `1cv8c.exe ENTERPRISE /WS http://localhost:8319/`.
Имя и пароль платформа ждёт С КАВЫЧКАМИ (`/N"<пользователь>" /P"<пароль>"`), поэтому
команда собирается СТРОКОЙ: список `subprocess` экранирует кавычки, пустой
пароль превращается в голое `/P`, и вместо входа открывается окно авторизации.
Всё это делает `инструменты/обновить_и_запустить.py`.

**Обновить конфигурацию ИБ командой нельзя.** У `1cedtcli` такой команды нет:
`infobase-import` — обратное направление (ИБ → проект), `export` — проект →
XML Конфигуратора. Скрипт запуска поэтому ЖДЁТ, пока EDT обновит базу (следит
за временем файла `1Cv8.1CD`). Чтобы ожидание проходило само, в EDT включается
«Обновлять конфигурацию информационной базы автоматически».

**База обновляется ТОЛЬКО через EDT.** Пользователь работает в 1C:EDT (проект
`УАТ_МВМ`, git); все скрипты кладут доработки в файлы этого проекта, EDT сам
обновляет конфигурацию ИБ. Любая загрузка мимо EDT (Конфигуратор, командная
строка) рассинхронизирует базу с проектом: EDT при следующем обновлении
останавливается с диалогом «конфигурация ИБ изменена независимо» и предлагает
полную выгрузку на десятки минут. Уже ловили; ответ в этой ситуации —
«Перезаписать» (источник правды — проект), предварительно закоммитив рабочее
дерево проекта. Выгрузка `ConfigUAT/` остаётся справочником метаданных для
скриптов, а НЕ каналом загрузки. Блок ниже про командную загрузку — история на
случай, когда EDT недоступен:

**Грузить только изменения — ТОЛЬКО из командной строки.** Окно «Загрузить
конфигурацию из файлов» в Конфигураторе грузит выгрузку целиком (30 тыс. файлов,
десятки минут), и `ConfigDumpInfo.xml` на это не влияет — проверено. Частичную загрузку
умеет лишь `1cv8.exe DESIGNER /F"<база>" /LoadConfigFromFiles "<выгрузка>" -files "<список>"
-updateConfigDumpInfo`. Готовый файл запуска делает `инструменты/команда_загрузки.py`
(находит платформу и базу сам), список файлов — `ConfigUAT-изменения.txt`.
`Configuration.xml` в списке обязателен, иначе новые объекты не увидят.

- **`.cmd` с кириллицей писать в cp866** (системная OEM-кодировка). В UTF-8 cmd.exe
  рассыплет имена файлов вроде `мвмСтруктураПредприятия.xml`.
- Перед загрузкой закрыть Конфигуратор и выйти из базы — нужен монопольный доступ.
- **Обязательны `/DisableStartupDialogs` и `/DisableStartupMessages`.** Без них
  `DESIGNER` в пакетном режиме открывает окно Конфигуратора и замирает на любом
  диалоге (авторизация, лицензирование). Ловили: 20 минут простоя, 9% процессора,
  база не тронута — со стороны выглядит как зависание.
- Строковый реквизит **длиннее 1024 не заводить**: обновление базы падает с
  «Ошибка SDBL: слишком большое значение описателя длины». Для длинного текста —
  неограниченная длина (0), так сделано в типовой 1876 раз.
- Отличить работу от ожидания: при перестроении растёт файл базы и загрузка
  процессора; при ожидании всё тихо, а `1Cv8.1CD` не меняется.
Имена типовой УАТ длинные и похожие (`уатМаршруты` и `ItobМаршруты`, `уатРейсыМаршрутов`,
`уатПутевойЛист` со 183 полями) — **сверять по CSV, а не по памяти.**

## Диспетчерский слой: какие документы что значат

Своих документов под заявку и рейс НЕ заводим — в УАТ они уже есть:

- **заявка** → `Документ.уатЗаказГрузоотправителя` («Заказ на ТС»). ТЗ-08 п.4.24
  уже привязал к нему заявку ERP, и вся типовая отчётность считает по нему.
- **рейс** → `Документ.уатМаршрутныйЛист` («Маршрутный лист»): в нём есть ТС,
  основание (тот самый заказ) и ТЧ «Заказы» — точки маршрута со временем,
  расстоянием и грузом.

Назначить машину = создать Маршрутный лист. Лист **записывается, но не
проводится**: проведение делает движения по регистрам и требует реквизитов
учёта, которых диспетчер не знает. Статус заявки нигде не хранится — он
вычисляется по её листам, чтобы не было двух источников правды.

Единицы: маршрутизация считает в **метрах и минутах**, УАТ хранит расстояние в
**километрах**, время в пути — в **часах**.

## Экран водителя опирается на типовые механизмы

Своего под АРМ водителя заводить почти нечего — типовая УАТ рассчитана на
мобильное приложение водителя (константа `уатИспользоватьМобильноеПриложение
Водителя`, регистры `уатСтатусыМобильногоПриложения`, `уатПользователиМобильного
Приложения`). Отсюда берём:

- **смена** — `уатПутевойЛист`: `Водитель1`/`Водитель2`, `ДатаВыезда`,
  `ДатаВозвращения`, **`ЗакрытВодителем`** (конец смены отмечает сам
  водитель), `ТранспортноеСредство`, `Смена`;
- **«не получается»** — `уатПричиныЗакрытияЗаказов` с реквизитом
  **«Использовать в мобильном приложении»**: список причин для водителя
  ведёт типовая, писать свой нельзя. Причина ложится в
  `ТЧ Заказы.ПричинаЗакрытияЗаказа`;
- **что за точка** — `ТЧ Заказы.ТипТочкиМаршрута`
  (`уатТипыТочекМаршрута`: Погрузка, Разгрузка, ПромежуточныйПункт,
  Дополнительная…). **Первая строка листа у нас ПОДАЧА**, а не погрузка:
  считать роль по номеру строки — врать водителю;
- **что сказал диспетчер** — `уатМаршрутныйЛист.КомментарийВодителю`.

**Карта рейса на телефоне** — SVG внутри HTML в поле HTML документа
(`мвмРейсыВодителя.КартаРейса`): подложка `data:`-картинкой из макета
`ПодложкаТелефон` обработки (ужатая копия подложки диспетчера, 2000 px,
64 цвета, ~300 КБ; пересобирает `обработка_арм_водителя.py`, когда
подложка диспетчера новее) плюс ломаная пути по узлам и изгибам проездов.
Единицы — плана (1500 × 1061, как в `src/map/10-core.js`), **ось Y у
плана вверх, у SVG вниз** — переворот `1061 − Y`. Три мелочи, на которых
легко споткнуться: `Base64Строка` режет текст переводами строк — внутри
data-URI их надо убрать; колонки реквизита-таблицы формы держать
НАДМНОЖЕСТВОМ колонок таблицы общего модуля (`ЗначениеВРеквизитФормы`);
карта — украшение и строится в `Попытка`, ключ пересборки — рейс плюс
отметки точек, иначе подложка летела бы по воздуху раз в минуту.

**Проверять АРМ водителя — на демо-наборе** (`инструменты/демо_данные_1с.py`,
кнопка посева в АРМ диспетчера): водитель Смирнов, машина Н453РУ190, семь
рейсов по заявкам ДЕМО-21…27 в состояниях «выполнен», «закрыт с
причиной», «на погрузке дольше норматива», «в пути» и три впереди;
путевые листы на сегодня у всех водителей, причины закрытия с галкой «для
мобильного», нормативы упаковок и время пунктов. Текущий пользователь
привязывается к физлицу Смирнова, если своего нет; для телефона заводится
ИБ-пользователь для демо-водителя (имя и пароль вычищены из skill pack) (роли `мвмВодитель`,
`БазовыеПраваБСП`, `уатБазовыеПрава`, `ЗапускМобильногоКлиента`).
Листы и путевые листы находятся по метке в комментарии — повторный посев
их перезаполняет, а не плодит.

**Чат водитель ↔ диспетчер — на типовых регистрах мобильного приложения**,
своего нет: `уатЧатыСВодителями` (сообщения, ключ Отправитель + Идентификатор),
`уатСтатусыСообщенийМобильногоПриложения` (доставлено/прочитано по
получателю), `уатЧаты` (чей чат; `ПолучитьТекущийЧатВодителя`, иначе
предопределённый `ОбщийЧат`). Создаёт сообщение вместе со статусом типовая
`уатЧатыСВодителями.СоздатьСообщениеМобильногоПриложения(Получатель, Текст,
Чат, Отправитель, Вид, …)`: от водителя — Отправитель = физлицо, вид
«Входящее», получатель — чат; от диспетчера — Отправитель = пользователь,
вид «Исходящее», получатель — физлицо. Обёртка — `мвмЧатВодителей`
(`инструменты/чат_водителей.py`), в АРМ диспетчера — шаг `чат_в_арм`
(раздел пакета `чаты`, команды `chatSend`/`chatRead`, `водительИд` в рейсе).

Правило экрана: «что показать и что разрешено нажать» решает ОДНА функция
общего модуля (`мвмРейсыВодителя.Экран`), форма только раскладывает ответ.
Состояний восемь: НетВодителя, НетСмены, НетРейсов, Выезд (точка подачи —
где машина стоит; одна кнопка «Выехал» закрывает её разом), Ехать,
НаТочке, Готово, СменаЗакрыта. На экране четыре закладки (Сейчас, Рейсы,
Чат, Смена): страницы «Маршрут» нет — операций две, погрузка и разгрузка;
верхней командной панели нет — экран обновляется сам, рейс выбирают в
списке. У таблиц `commandBarLocation None`: иначе телефон рисует «More
actions» на языке устройства; булевы колонки на телефоне показываются
словом «No» — в списках их не держать.

## Оформление плана — справочники 1С

Вид узлов, проездов и геозон больше не зашит в карту: он приходит разделом
пакета `оформление` из трёх справочников — `мвмТипыУзлов`, `мвмТипыПроездов`,
`мвмТипыГеозон`. **Код элемента — это ключ карты** (`jn`, `load`, `storage`…),
им стороны и сходятся. Генератор общего модуля —
`инструменты/оформление_карты.py`, он же держит умолчания, снятые с карты.

- Значение берётся по трём ступеням: своё у объекта → умолчание ЕГО ТИПА →
  общее умолчание карты (`CFG`). Пустая строка считается незаданной: 1С
  отдаёт незаполненный реквизит именно ею.
- **Своего оформления у узла и геозоны больше нет** — вид задаёт тип. Цвета и
  размеры в типах хранятся ПЕРЕЧИСЛЕНИЯМИ (`мвмЦветНаКарте`,
  `мвмРазмерШрифтаНаКарте`): поле со списком вместо строки, куда надо вписывать
  `#rrggbb` по памяти. Единая таблица «значение → hex» —
  `инструменты/палитра_карты.py`, она же дописывает недостающие оттенки в само
  перечисление. У геозоны остались типовые «Цвет на карте» и «Размер шрифта»
  (ТЗ-08 п.6.5) и позиция названия: это про конкретную зону, а не про тип.
- **Ссылка на тип обязательна**, поэтому миграция обязана пройти ДО того, как
  кто-то попробует записать старый объект: `МигрироватьТипы()` зовётся из
  `ОформлениеДляПакета()`, то есть при каждой сборке пакета. Пока миграция не
  прошла по всей базе, перечисление `ТипУзла` удалять нельзя — по нему тип и
  восстанавливается.
- **Какие типы узлов видны диспетчеру, решает справочник** (`ПоказыватьУДиспетчера`):
  перекрёстков и точек на плане сотни, и они закрывают собой цеха. В редакторе
  графа видно всё всегда — там их правят. Булево не отличает «не заполняли» от
  «сняли галку», поэтому первичная простановка идёт по косвенному признаку: не
  стоит НИ У ОДНОГО типа — значит никто и не ставил.
- **Время погрузки и разгрузки — у ПУНКТА НАЗНАЧЕНИЯ** (`ВремяПогрузки`,
  `ВремяРазгрузки`, в минутах). Порядок: стоянка из строки заказа → время
  пункта → типовая «Стоянка (п/р)» (она в ЧАСАХ и одна на обе операции) →
  общая настройка «нормативы» → зашитые 15 и 10 минут.
- **Типы транспорта в правилах геозоны — ссылки на `уатТипыТС`**, а не свой
  список. Карта показывала пять зашитых («Фура», «Самосвал»…), 1С искала их по
  GUID и не находила: галки были пусты всегда, а сохранение зоны ОЧИЩАЛО
  табличную часть вместе с тем, что завели руками. Правило: если карта прислала
  список, в котором ни один идентификатор не разрешается в ссылку, — часть не
  трогать (`НечегоПисать`).
- **Весогабариты геозоны — РЕКВИЗИТЫ шапки** `МаксВес`, `МаксШирина`,
  `МаксВысота` рядом с `МаксСкорость` (длины у зоны нет). Раньше это была наша
  ТЧ `ВесогабаритныеОграничения`: у зоны ограничение одно, а таблица требовала
  строки ради трёх чисел и отдельного запроса «самое строгое». ТЧ пока
  оставлена ИСТОЧНИКОМ МИГРАЦИИ — `МигрироватьОграниченияЗон()` зовётся при
  каждой сборке пакета; удалять её можно только после того, как перенос
  прошёл по всей базе (тот же приём, что с перечислением типов узлов).
  Типовая у геозоны только `Координаты` (Лат/Лон) — она под GPS-зоны
  мониторинга, к плану завода отношения не имеет.
- **Контур зоны на плане — наша ТЧ `КонтурНаПлане`** (X, Y в единицах плана,
  порядок по номеру строки). Именно ТЧ, а не реквизиты: точек много. У узла
  и проезда координаты, наоборот, в шапке — точка там одна.
- **Тип проезда — это КЛАСС ДОРОГИ** (уличный, внутрицеховой, узкий, ж/д
  переезд), а не категория отрисовки. Он несёт и вид линии, и ограничения:
  скорость, вес, габариты, задержку. Ограничения типа **сильнее геозоны** —
  зона описывает территорию, а тип саму дорогу; каждое правило зоны работает
  только там, где у типа своего предела нет. У ребра осталось одно
  направление: односторонность — свойство участка, а не класса.
- Зашитые `NODE_STYLE`/`GEO_TYPES`/`CFG.road` остались запасным набором для
  демо-режима в браузере — не удалять.
- Тип узла хранится И ссылкой (`Тип`), И прежним перечислением (`ТипУзла`):
  перечисление читают запросы, а новый тип, придуманный в справочнике, в него
  не помещается. При чтении ключ берётся из кода ссылки, при пустой — из
  перечисления; так мигрируют узлы, заведённые до справочников.
- Палитра типов на вкладке «Настройки» в связке с 1С отключается: иначе
  правка ушла бы в настройки карты, а справочник перекрыл бы её следующим
  пакетом.

## Интеграция с 1С (граница адаптации)

Карта и 1С развязаны через **фиксированный JSON-пакет** (контракт). От метаданных зависит
только тонкий слой: **запросы/запись в `Module.bsl`** и объекты конфигурации. Карта/
планировщик/UI от метаданных НЕ зависят. Переезд на боевой УАТ — в основном переписывание
запросов модуля под реальные имена — не трогая прототип. Полностью:
`03-1С-интеграция/1С-МЕТАДАННЫЕ-И-ПЕРЕЕЗД-НА-УАТ.md` и `ВНЕДРЕНИЕ-1С.md`.
