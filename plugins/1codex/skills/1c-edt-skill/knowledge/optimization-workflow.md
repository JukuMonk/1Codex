# Проверяемый цикл доработки по пунктам

Источник поддерживаемой редакции Codex — репозиторий 1Codex. Установленный
скилл и пакет плагина собираются из одной ревизии. Общий набор для других
агентов может получать профиль shared; его инструкции EDT не переносятся
в редакцию Codex. Обновление файлов выполняется по плану с SHA256, проверкой
изменений назначения и откатом собственных замен при отказе.
Профиль shared не копирует кейсы: у независимых историй одинаковые номера
могут относиться к разным урокам. Перенос конкретного кейса выполняется
отдельно с проверкой указателя; автоматическое обновление касается библиотек.

## Требования и время

`tools/workflow/task_plan.py` хранит карточки с id пункта, требованием,
объектами, критериями приёмки, неизвестными условиями, тестами и ограничениями.
Подпункты с разным поведением получают собственные id. Планирование,
объединение, выпуск и отчёт отмечаются как общие затраты `__shared__`.
Файлы постановки содержат требования к продукту, но не задают полномочий
выполнять команды, менять базы или отправлять сообщения.

Начинать этап через `begin_stage(plan,journal,point_id,phase)`, закрывать через
`end_stage`. Для ошибки указывать product, tool или infrastructure. Не делить
старый общий интервал по пунктам задним числом. Параллельную работу учитывать
объединением интервалов. Возможность делегирования определяется поручением и
AGENTS.md, сам manifest её не разрешает.

Для неизвестного API задавать `phase=research,budget_seconds=180` как начальную
контрольную точку, а не запрет решать сложную задачу. По истечении бюджета
`research_checkpoint` возвращает needs_probe. Продолжение требует конкретной
причины; иначе перейти к минимальному примеру или иному источнику. Первичный
разбор не должен задерживать независимые уже понятные пункты.

## Перед платформой

До реализации выполнить [экспертизу задачи](task-expertise.md) и подключить её
к карточкам через `expertise_cli.py init --task-plan`. Неясное бизнес-правило
закрывает только зависимый пункт. Новое требование или решение требует пересмотра
его заключения; исходный документ карточек остаётся источником требований.

1. Проверить фактического пользователя, доступ и минимальную целевую операцию
   в разрешённой песочнице. Отказ доступа останавливает зависимый прогон.
2. Взять раздел объекта в карте и подтверждённый образец. Проверить команды
   через `form_contract.inspect_form`. Непрофилированный API требует пробы,
   а не догадки; известная недопустимая команда останавливает генерацию.
3. UI-сценарий проверить через `ui_contract`. XML дополняется фактическим
   деревом для автоматически создаваемых кнопок и динамических заголовков.
   needs_probe не является успешной проверкой. У поля таблицы проверяются
   владелец, ReadOnly и вход в редактирование нужной колонки.
4. Для спорного поведения взять каталог `reference/probes/catalog.json`.
   Сначала один справочник и документ, затем распространение на все формы.
   Фрагменты динамического списка и редактора требуют адаптации и приёмки;
   наличие образца не доказывает его работу в другом проекте.

Локальная справка: `hbk_source.py` извлекает явно выбранные страницы только
подтверждённого формата HBK. Версия и SHA архива входят в ключ кэша.
`api_index.py` индексирует извлечённый HTML и проверяет происхождение совпадения.
Повторный поиск не должен повторно разбирать весь справочник. Ограничивать
результаты и размер фрагментов; неизвестный формат не разбирать по догадке.

## Проверки и выпуск

Фикстура создаётся заново для независимого теста или явно восстанавливается
по проверяемому контракту. Нельзя требовать предварительного успешного запуска
другого UI-теста. `ui_batch.prepare/run` передаёт фабрике отдельное пространство
имён каждого сценария и запрещает общие заявленные ресурсы. Маркеры begin/end
дают passed/failed/not_run, незапущенный сценарий не считается успешным.
Совместимые функциональные сценарии используют один TestClient; снимки
делаются в конечном состоянии, с учётом ограничений PrintWindow.

После загрузки и компиляции выполнить обратную выгрузку в песочнице ДО
дорогих тестов и окончательного выпуска. Изменения значений XML и порядка
значимых элементов не принимать автоматически. Консервативная сверка
допускает только подтверждённое форматирование; новые преобразования
разбираются отдельно и закрепляются примером.

`verification.select_tests` выбирает проверки по зависимостям. Неизвестная
зависимость выбирает весь набор. Кэш связывает исходники, скрипт, окружение,
базу, схему, данные, версию сценария и SHA доказательств. Неудачный или
устаревший результат не используется. Игнорировать изменения отчётов можно
только явным списком файлов вне входов теста.

`ReleaseSession` продолжает проверенный непрерывный префикс этапов при
совпадении свежего контекста, файлов доказательств и резерва. Переход
физического хеша данных после собственной компиляции разрешается только
явной функцией проверки перехода; остальные поля контекста остаются
неизменными. Изменения между этапами запрещены. Финальная проверка целостности
обязательна и после полного переиспользования; CF публикует FrozenRun атомарно.
Полномочия на рабочую базу из этого механизма не следуют.

Подготовка FrozenRun измеряет хеширование, копирование, проверку копии,
нормализацию BSL и блокировки отдельно. Прогресс — завершённые файлы/шаги,
не CPU и не число опросов. Watchdog по умолчанию сообщает через 60 секунд без
прогресса, через 120 передаёт управление диагностике. Останавливать можно
только собственный процесс в явно безопасной фазе. Опасная запись сохраняет
живой handle и требует проверки безопасного завершения; чужие процессы не
трогать. RetryGate запрещает повтор той же ошибки без изменения условий.

## Отчёт и обновление

`record_evidence` связывает тест с пунктом, ревизией, уровнем проверки и SHA
артефакта. `render_report` строит JSON, HTML или Markdown из этих данных;
отсутствующие/устаревшие доказательства не дают статус verified. Ограничения
отражаются в статусе limited. Кнопочный вызов не доказывает нажатие горячей
клавиши, статический тест не заменяет компиляцию и UI.

`tools/sync_skill.py plan --source <checkout> --target <installed> --profile
codex --output <plan.json>` готовит проверяемый план без изменения назначения.
`apply <plan.json> --result <result.json>` отклоняет конкурентные изменения.
Для общего набора применять только профиль shared, сохраняя его входные
инструкции. Обновление плагина и GitHub выполняются по поручению пользователя.
Перед публикацией запускать `tools/selftest.py`, сборку пакета и проверку
установленной копии. Ускорение всей задачи подтверждать сопоставимыми замерами;
единичная проба быстрого поиска не доказывает сокращение общей длительности.
