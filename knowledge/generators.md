# Генераторы вместо ручной правки XML

Так был сделан весь проект-источник: 80 скриптов на Python, каждый кладёт
свои файлы в проект EDT идемпотентно. Здесь — сама техника; образцы в
`reference/generators/`, библиотека — `tools/edt_lib.py`.

## 1. Зачем (HIGH)

- XML форм и метаданных длинный и однообразный: поле — 40 строк, таблица —
  200. Ручная правка ошибается в порядке тегов и номерах (cases 001–004).
- Выгрузки типовой в git нет (760 МБ), значит источник правды по доработкам
  — сам скрипт со спецификацией наверху (`метаданные_edt.py`: список объектов
  и реквизитов → файлы).
- Пересборка модуля из цепочки шагов даёт воспроизводимость: прямая правка
  собранного файла теряется при следующей сборке — новая доработка модуля
  добавляется отдельным шагом и вписывается в таблицу цепочки.

## 1a. Не с нуля (HIGH)

Новый проект начинает не с изучения форматов, а с `tools/edt_lib.py`: там
сборка `.mdo` всех видов, форм (поля, группы, страницы, таблицы со
спутниками), схем компоновки, вставок в модули и регистрации в конфигурации.
Генератор проекта — спецификация объектов плюс вызовы библиотеки; чего в
ней нет — дописывается в неё, а не рядом. Ловили: вторая сессия на новой
конфигурации потратила часы на «повторить форматы проекта один в один»
(1200 строк), хотя всё это уже лежало в `edt_lib`.

## 2. Правила идемпотентности

- Повторный запуск не дублирует: элемент ищется по `<name>`/`<segments>`,
  реквизит — по `<name>`, вызов в процедуре — по подстроке.
- Якорь вставки задаётся СОДЕРЖИМЫМ с переводом строки и отступом
  (`\r\n  </attributes>\r\n`), а не номером строки и не голым тегом
  (ловили: голый `</attributes>` совпал с закрытием реквизита внутри ТЧ — см. `tools/edt_lib.add_attributes_to_mdo`).
- Якорь для кода — директива вместе с объявлением (case 012).
- uuid берётся из существующего файла, иначе устойчивый uuid5 (case 020).
- Вставки собираются как `(позиция, строки)` и применяются снизу вверх,
  чтобы номера строк не поехали.
- Проверка «уже применено» — только `стало in текст`. Условие
  `стало in текст and было not in текст` ложно, когда `стало` начинается с
  `было`, и второй прогон вставляет всё дважды (case 056). Прогонять шаг
  дважды подряд; считать объявления против завершений.
- Ключ `--проба`: собрать и проверить, не записывая.
- Свою область в чужом модуле (`#Область Мвм…` … `#КонецОбласти`)
  переписывать целиком — её текст растёт от шага к шагу; идемпотентная
  вставка «если нет» не обновляет старую редакцию.

## 3. Проверки внутри генератора (HIGH)

Перед записью: XML разбирается (`ET.fromstring`), CRLF, без BOM, дубли id,
`saveWindowSettings`, `numberQualifiers`, номера реквизитов/колонок, пути
данных ведут к реквизитам объекта (`реквизиты_объекта` читает `.mdo`),
обработчики и команды описаны в модуле, состав подсистемы существует, право
роли — на существующий объект, запросы (кавычки, псевдонимы, группы,
пакеты), директивы и клиентские вызовы, чужие вызовы между модулями.
Всё это — `tools/check_project.py`, `tools/check_bsl.py`.

«Валидный XML ≠ правильный XML»: `ET.parse` пропустил файл, где значение
уехало в соседний тег (`<v8:Length>	</v8:Length>1000`); проверка
«осмысленности» — у листьев нет текста из одних пробелов, квалификаторы
числовые, после закрывающего тега не болтается текст (case 025).

## 4. Пользователь правит формы в EDT (HIGH, case 027)

Пользователь настраивает форму в EDT (перетаскивает группы, меняет
раскладку) — и это надо переносить в генератор, иначе пересборка сотрёт.
Порядок: HEAD проекта EDT → прогнать генераторы → сравнить с текущим файлом
пользователя (`reference/generators/выделить_правки.py`); всё в разнице —
либо его правка, либо то, как EDT переписал наш XML. Цель — «строк разницы
0»: тогда пересборка ничего не теряет. Отсюда правило писать XML в порядке
EDT и не писать умолчаний.

## 5. Порядок запуска и укладки

Цепочка сборки модуля АРМ (`СБОРКА-МОДУЛЯ.md` проекта-источника): шаги в
строгом порядке, укладка последним шагом, укладчик прогоняет все проверки и
не пускает негодный файл в EDT. `build` сборки страницы обновляет только
`dist/`; без укладки макета в проект база показывает старую страницу —
ловили «ничего не вижу» (обязательный шаг в CLAUDE.md проекта).

Общие правила скриптов на Windows: читать и писать файлы `newline=''`
(иначе Python подменит `\n` на `\r\n`), вывод в UTF-8, `.cmd` с кириллицей
в cp866, heredoc в Git Bash рвётся на больших файлах и портит `\\` —
писать файлы инструментом, а не `cat <<EOF`.
