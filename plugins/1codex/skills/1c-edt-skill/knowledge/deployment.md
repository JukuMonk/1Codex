# Обновление базы из EDT и доставка изменений

## 1. Главное (HIGH)

- **База, связанная с проектом EDT, обновляется из EDT.** Это правило не относится к отдельной базе в режиме XML Конфигуратора. В текущем проекте без EDT использовать `knowledge/designer-format.md`. Любая загрузка мимо EDT (Конфигуратор,
  командная строка) рассинхронизирует базу с проектом: EDT при следующем
  обновлении останавливается с диалогом «конфигурация ИБ изменена независимо»
  и предлагает полную выгрузку на десятки минут. Ответ в этой ситуации —
  «Перезаписать» (источник правды — проект), предварительно закоммитив
  рабочее дерево проекта.
- **Команды «обновить конфигурацию ИБ» у `1cedtcli` нет**: `infobase-import`
  — обратное направление (ИБ → проект), `export` — проект → XML
  Конфигуратора (только целиком, частичной выгрузки нет — проверено на
  EDT 2026.1). Скрипты, которым нужна обновлённая база, ЖДУТ, пока EDT
  обновит (следят за временем файла `1Cv8.1CD`); в EDT включается
  «Обновлять конфигурацию ИБ автоматически».
- **Правку файлов снаружи EDT подхватывает после обновления проекта** (F5).
  Формы, открытые в редакторе, снаружи не переписывать (case 028).

## 2. Полное и инкрементальное обновление (HIGH, case 020)

«Ошибка добавления объекта DataProcessor uuid=… : нельзя добавлять объекты
метаданных без загрузки родительского объекта» — не про формы и не про uuid:
инкрементальная загрузка умеет МЕНЯТЬ существующие объекты, но не ДОБАВЛЯТЬ
новые. Когда в проекте появились обработки, отчёты, роль, общий модуль,
подсистема с дочерними — первое обновление конфигурации ИБ должно быть
полным; дальше снова хватает инкрементального. Отсюда:

- uuid объектов держать УСТОЙЧИВЫМИ (`edt_lib.stable_uid`): пересборка со
  случайным uuid делает объект новым;
- пробные объекты удалять сразу после эксперимента;
- новый реквизит существующего объекта проходит инкрементально, но требует
  реструктуризации (монопольный доступ).

## 3. Что ломает обновление при валидных файлах (HIGH)

| Симптом при обновлении базы | Причина | Case |
|---|---|---|
| «Ошибка SDBL: слишком большое значение описателя длины» | строковый реквизит длиннее 1024; для длинного текста — неограниченная длина 0 | 024 |
| «Свойство Use/FillValue не входит в состав объекта метаданных Attribute» (формат Конфигуратора) | состав свойств реквизита зависит от владельца (справочник / ТЧ / документ) | 025 |
| «нельзя добавлять объекты без загрузки родительского» на дочерней подсистеме | нет `<parentSubsystem>` или новая подсистема при инкрементальном обновлении | 019, 020 |
| «NullPointerException … "formItem" is null» при экспорте | сломана модель рабочего пространства EDT, файлы целы; «Проект → Очистить…» | 028 |
| «Файл объекта не существует …/Subsystems/X.xml» при полном импорте | объекта нет в модели — нет `parentSubsystem` | 019 |

## 4. Проверка файлов без EDT (MEDIUM)

`1cedtcli -data <чистое рабочее пространство> -command export --project
<проект> --configuration-files <папка>` — 10–15 минут; если выгрузка прошла,
а обновление базы из EDT падает — сломана модель рабочего пространства, а
не файлы (`reference/generators/проверить_экспорт_edt.py`). Два `1cedtcli`
в одном рабочем пространстве — «IWorkspaceOrchestrator unavailable»:
запускать по одному.

## 5. Автономный сервер EDT и файловая база (MEDIUM, история)

Пока автономный сервер (`ibsrv.exe`, порт из `config.yaml`) держит каталог
базы, открыть его файлом нельзя: клиент стартует и молча исчезает.
Подключаться как EDT: `1cv8c.exe ENTERPRISE /WS http://localhost:8319/`.
Имя и пароль платформа ждёт С КАВЫЧКАМИ (`/N"<пользователь>" /P"<пароль>"`), поэтому
командная строка собирается СТРОКОЙ, а не списком аргументов.

## 6. Доставка изменений на сервер без EDT (анализ, LOW — не внедрялось)

Частичная загрузка умеет только `1cv8.exe DESIGNER /F"<база>"
/LoadConfigFromFiles "<выгрузка>" -files "<список>" -updateConfigDumpInfo`
при постоянной полной выгрузке с согласованным `ConfigDumpInfo.xml` на
сервере; `Configuration.xml` в списке обязателен, иначе новые объекты не
увидят. Обязательны `/DisableStartupDialogs /DisableStartupMessages` — иначе
пакетный Конфигуратор ждёт диалога молча (20 минут простоя). `.cmd` с
кириллицей — в cp866. Схема «git-репозиторий выгрузки как детектор и
транспорт изменений» описана, но не прогонялась.

Прогнано на МВМ (case 091, MEDIUM→HIGH для этой схемы): «дельта-пакет» — изменённые объекты верхнего уровня
целиком, загрузка `/LoadConfigFromFiles <files> -listFile <список>` + `/UpdateDBCfg`. Корень — один объект:
`Configuration.xml` + все корневые `Ext/**` (с `ParentConfigurations` — поддержкой); без них загрузка стирает
модули приложения и сеанса, интерфейс, справку и поддержку. Пакет проверять на копии эталона: выгрузка после
загрузки = «стало», кроме `ConfigDumpInfo.xml`.

## 7. После обновления

- Первое открытие каждой новой формы — в тонком клиенте; мобильную — и в
  мобильном.
- Демо-посев на боевых данных не запускать: посевы находят и перезаполняют
  объекты по меткам, но пользователи там настоящие.
- Новое — в подсистему и справку тем же коммитом; коммит после каждого
  рабочего шага (точка отката).

## 8. Веб-публикация: фоновые задания (HIGH, case 073)

- `default.vrd` с `<debug enable="true" … url=""/>` — каждый фоновый сеанс падает с «Ошибка регистрации
  предмета отладки в отладчике»: отчёты БСП в веб-клиенте — «пустой результат», фоновые расчёты — ошибка.
  Для работы: `<debug enable="false"/>` (или адрес работающего `dbgs`), перезапуск веб-сервера.
- Файловая база через веб-сервер: фоновые задания выполняются в процессе веб-сервера и занимают лицензии;
  «Не обнаружено свободной лицензии!» — нехватка сеансов (версия «для разработчиков»).
- Проверка без правок: `…/ru_RU/?C=РежимОтладки` — длительные операции БСП без фонового задания.
- Клиентский код для веб-клиента — без `ЗаписьJSON`/`ЗаписатьJSON` (в веб-клиенте их нет).
