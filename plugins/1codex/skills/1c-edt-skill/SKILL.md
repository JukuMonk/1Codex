# Разработка 1С в ChatGPT и Codex без EDT

Сначала прочитать [правила среды ChatGPT](knowledge/chatgpt.md). Они уточняют доступность инструментов в текущем чате; затем применять рабочий цикл и материалы ниже.

Набор содержит 116 кейсов.

## Начало задачи

В новой задаче разработки 1С открой «Монитор 1Codex» до анализа и правок.
Найди скрипт <code>tools/workflow/pipeline.py</code> относительно **этого SKILL.md**.
Передай Python абсолютный путь к скрипту и аргументы
<code>start --project "каталог проекта" --label "краткое имя задачи"</code>.
В настольном Codex при доступном <code>open_in_codex</code> добавь
<code>--no-browser</code> и сразу открой выведенный HTTP-адрес этим инструментом
как <code>target.type = browser</code> в текущем чате. Если панели нет,
обычный <code>start</code> сам открывает системный браузер.
Если панель не открылась, используй <code>open ПУТЬ_К_ЖУРНАЛУ</code> для
того же запуска. Дай ссылку в чат и записывай реальные этапы в этот журнал.
При продолжении задачи используй существующий журнал. Если Python выполняется
на удалённой машине, используй автономный экспорт для коллеги.

Основной формат — иерархическая XML-выгрузка Конфигуратора.
Использовать `tools/designer_lib.py`; EDT и `1cedtcli` не применять.
BSL-проверки — `tools/bsl_checks.py`, СКД — `tools/skd_builder.py`.
Старые импорты edt_lib сохранены для совместимости.

Сначала прочитать [правила Codex](knowledge/codex.md), затем выбрать задачу в
[маршрутах без EDT](index/designer.md) и прочитать только нужный раздел.
Новый проект — [порядок старта](knowledge/new-project.md).

Доработка по ДиЗ или нескольким требованиям — [цикл по пунктам](knowledge/optimization-workflow.md):
карточки и время, ограниченное исследование, контракты форм/UI, независимые
фикстуры, ранняя сверка, проверяемое переиспользование результатов и отчёт.
Инструкции, профиль платформы и уровни приёмки не заменять общим быстрым режимом.

## Рабочий цикл

Перед реализацией выполнить [экспертизу задачи](knowledge/task-expertise.md):
проверить непротиворечивость требований и архитектурные предположения, для каждой
критики предложить выход и приёмочный пример. Принятое в постановке правило
повторно не спрашивать; отличие старого кода разобрать как задачу реализации.
Простая правка допускает короткое заключение без замечаний. Вопросы блокируют
только зависимые пункты. Заключение сохранять через `expertise_cli.py`; при
карточках подключать `--task-plan`, чтобы начало реализации проверяло допуск.
В мониторе использовать отдельную ветвь `expertise`.

1. Зафиксировать версию платформы, совместимость, формат выгрузки, префикс,
   тестовую базу и статус конфигурации: своя, поставщика или расширение.
2. Прочитать раздел объекта в `КАРТА.md`; карта — `tools/config_map.py`.
   При отсутствии карты сначала сверить метаданные и рабочий аналог целевой версии.
3. Брать образец нужного формата. Кейсы 078, 079, 084 — своя конфигурация;
   074 — внешняя обработка; 081–083 — расширения и перенос; 091 — дельта-пакет.
   Проектные пути и данные из `reference/` и кейсов не переносить.
4. Генерировать XML через `designer_lib`, BSL править с сохранением кодировки.
   Существующие UUID сохранять. Повторная генерация не стирает принятые правки.
   XML/BSL выгрузки — UTF-8 с BOM, CRLF; SVG — без BOM.
5. Прогнать `tools/check_designer.py <выгрузка>` и `tools/lint_dump.py <выгрузка>`. Новые ошибки исправлять,
   не добавлять их в baseline. Линт не заменяет компиляцию и выполнение.
6. Проверить в отдельной тестовой базе: загрузка, UpdateDBCfg, CheckModules,
   обратная выгрузка и сверка. Полная загрузка допустима для своей конфигурации;
   для поставщика сохранять корневые `Ext/**` и поддержку (кейс 091).
7. Данные и отчёты проверить через COM, формы и команды — TestManager/TestClient
   либо Vanessa. В отчёте назвать фактически выполненные уровни проверки.

## Обязательные замеры времени

Сразу после запуска «Монитора 1Codex» открой этап учёта времени с узлом
`learning.journal` («Замеры») в журнале текущего прогона. Записывай операции
в их узлах атласа. Перед завершением зафиксируй в ветке «Замеры» объединение
интервалов (`learning.normalize`), непокрытое время и основные фактические
длительности (`learning.cost`). Проверь в мониторе, что в этой ветке видны
выполненные шаги. Используй для замеров журнал текущего прогона.

Во **всех задачах разработки на 1С**, включая небольшие правки, вести журнал
времени по этапам с начала задачи до отчёта: [порядок и команды](knowledge/task-timing.md).
Вести журнал, открытый в начале задачи, до итогового отчёта.
Ручным шагам указывать узел атласа, проверкам передавать журнал. Ошибку,
исправление и повтор записывать отдельными попытками. Для нескольких пунктов
использовать карточки требований. [Монитор и команды](knowledge/pipeline-monitor.md).
Учитывать анализ, реализацию, проверки, исправления, ожидания и выпуск, если
они выполнялись. Не складывать вложенные и параллельные интервалы. В отчёте
показывать фактические длительности и пробелы в замерах; время процесса
не называть чистым временем Codex. Если правило подключено посреди задачи,
начать замер сейчас и явно указать, какая часть не измерена.
